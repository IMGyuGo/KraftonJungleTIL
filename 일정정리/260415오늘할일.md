1. 수요코딩회 (B+)

- 노드는 최대 ceil(M/2)개 부터 M개의 자식
- 노드에는 최대 ceil(M/2)-1개부터 (M-1)개의 키
- 노드의 키가 x개라면 자식의 수는 x+1개
- 최소차수는 자식수의 하한값, 최소차수가 t라면 M = 2t-1을 만족
  (최소차수 t가 2라면 3차 B트리, key의 하한은 1개)

# B+ 트리

## 개념 정리

### 차수 M이 의미하는 것

```
B+ 트리에서 차수(order) M은 보통 이렇게 정의

=> 한 노드가 가질 수 있는 최대 자식 수

자식 수 : 최대 M개
키 수 : M-1개

최소값이 왜 M/2냐?
=> 트리는 균형을 유지해야 하기 때문에
=> 너무 적게 채워지면 트리가 한쪽으로 무너짐 (성능 O(N) 위험)

그래서 규칙이 존재
자식 수
- 최소 ceil[M/2] ~ [M]
키 수
- 최소 [ceil(M/2)-1] ~ [M-1]

자식을 1개로 두면, 그냥 링크드리스트가 되어버림
[10] - [20] - [30]
```

### 왜 DB 인덱스 설계는 B+ 트리를 사용할까?

```
"디스크 I/O 최소화 + 범위 조회 최적화" 때문에 B+ 트리를 사용

1. 전체: DB는 "메모리"가 아니라 "디스크" 문제

- 자료구조 비교할 때 대부분 이렇게 생각
- BST : O(logN)
- Hash : O(1)
- 근데 DB에는 이게 핵심이 아님

진짜 비용
-> 디스크 I/O (페이지 읽기)
    - 메모리 접근 : ~100ns
    - 디스크 접근 : ~1ms (10,000배 이상 느림)
    -> 따라서 트리 깊이를 최소화해서 디스크 접근 횟수를 줄이는 게 목적

2. 왜 BST를 안 쓸까?
- 문제
    - 노드 (key 1개)
    - fan-out (자식 수) = 2
    -> 결과적으로 트리 높이 깊어지고, 디스크 접근 횟수도 높아짐
- 100만개 데이터 : BST(20), B+트리(~3~4)

3. 왜 Hash Table은 안 쓸까?
- 문제1 : 범위 조회 불가능
    - SELECT * FROM user WHERE age BETWEEN 20 AND 30;
    - 해시는 순서가 없음
- 문제2 : 정렬 안됨
    - ORDER BY age (해시는 재 정렬 필요 (느림))
- 문제3 : 디스크 지역성 나쁨
    - 해시 -> 랜덤 접근
    - 디스크 -> 순차 접근이 빠름

4. 왜 B-트리는 안 쓸까?
- 내부 노드에도 데이터가 있어서 범위 조회 시 비효율적이고
- 구조가 정말 복잡하고

5. B+ 트리
    1. 트리 높이가 낮다.
    2. 범위 조회가 압도적으로 빠르다.
        - [10 | 20 | 30]
    - 리프 : [1~9] -> [10~19] -> [20~29] -> ...
    3. 캐시효율 좋다. (내부노드는 작고 자주 쓰임)
    4. 디스크 구조와 잘 맞음
        - DB는 페이지 단위로 읽는데, B+트리 -> 노드 = 페이지크기
    5. 삽입 삭제 안정성 (항상 균형 유지)
```

| 구조       | 조회    | 범위 조회 | 디스크 효율 | DB 적합 |
| ---------- | ------- | --------- | ----------- | ------- |
| BST        | O(logN) | ❌        | ❌          | ❌      |
| Hash       | O(1)    | ❌        | ❌          | ❌      |
| B-Tree     | O(logN) | △         | ⭕          | △       |
| **B+Tree** | O(logN) | ⭕        | ⭕⭕⭕      | ✅      |

### DB 내부에서 B+ 트리가 페이지 단위로 어떻게 저장되는걸까?

슬롯배열

- B+트리의 노드 = 디스크 페이지 (보통 4kB)

```
┌──────────────────────┐
│ Page Header          │
├──────────────────────┤
│ Slot Array           │  ← 인덱스 (offset 리스트)
├──────────────────────┤
│        ...           │
│   Free Space         │
│        ...           │
├──────────────────────┤
│ Records (Data Area)  │  ← 실제 row or key
└──────────────────────┘
```

## key 삽입 과정

### Case 1. 분할이 일어나지 않고, 삽입 위치가 리프노드의 가장 앞 key 자리가 아닌 경우

- B 트리와 똑같은 삽입 과정

### Case 2. 분할이 일어나지 않고, 삽입 위치가 리프노드의 가장 앞 key 자리인 경우

- 삽입 후 부모 key를 삽입된 key로 갱신하고, data를 넣어줌

### Case 3. 분할이 일어나는 삽입 과정

- 분할이 일어나는 노드가 리프노드가 아니라면 기존 B 트리와 똑같이 분할을 진행, 중간 key를 부모 key로 올리고, 분할한 두개의 노드를 왼쪽, 오른쪽 자식으로 설정
- 분할이 일어나는 노드가 리프노드라면 중간 key를 부모 key로 올리지만, 오른쪽 노드에 중간 key를 포함하여 분할, 또한 리프노드는 연결리스트이기 때문에 왼쪽 자식노드와 오른쪽 자식 노드를 이어줘 연결리스트 형태를 유지함

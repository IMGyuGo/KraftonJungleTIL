# 9.9 동적 메모리 할당

- 할당기
  - 구체성을 위해서 힙 메모리를 관리하는 할당기

- C 표준 라이브러리
  - malloc 패키지로 알려진 명시적인 할당기를 제공

- implict (묵시적 할당기)
  - 언제 할당된 블록이 더 이상 프로그램에 의해 사용되지 않고 블록을 반환하는지를 할당기가 검출할 수 있을 것을 요구
  - 묵시적 할당기는 garbage collector로 알려져 있음, 자동으로 사용하지 않은 할당된 블록을 반환시켜주는 작업을 가비지 컬렉션이라고 부름

- explicit (명시적 할당기)
  - 응용이 명시적으로 할당된 블록을 반환해 줄 것을 요구
  - 예를 들어, C 표준 라이브러리는 malloc 패키지라고 하는 명시적 할당기를 제공
  - C 프로그램은 malloc 함수를 호출해서 블록을 할당하며, free 함수를 호출해서 블록을 반환한다. C++에서 new와 delete 호출이 유사

- seglist ()

### malloc 함수

- 블록 내에 포함될 수 있는 어떤 종류의 데이터 객체에 대해 적절히 정렬된 최소 size 바이트를 갖는 메모리 블록의 포인터를 리턴

```
최소 size의 바이트를 갖는 메모리 블록의 포인터를 리턴?

-> 32비트 모드 (gcc -m32) [항상 8의 배수인 블록을 리턴]
-> 64비트 모드 (기본설정) [16의 배수]

만일 malloc이 문제를 만날 시
(ex. 프로그램이 가용한 가상메모리보다 더 큰 크기의 메모리 블록을 요청하는 경우)
return NULL 리턴 후, (errno를 설정)

Malloc은 리턴하는 메모리를 초기화 하지는 않음
초기화한 동적 메모리를 원하는 응용들은 calloc을 사용할 수 있음 -> 할당된 메모리를 0으로 초기화하는 calloc 함수 주위의 얇은 래퍼 함수
이전에 할당된 블록의 크기를 변경하려는 응용은 realloc 함수 사용 가능

malloc같은 동적 메모리 할당기는 mmap과 munmap 함수를 사용해서 명시적으로 힙 메모리를 할당하거나 반환하며, 또는 sbrk 함수를 사용할 수 있음
sbrk -> 힙의 꼭대기를 가리키는 것?
```

## 9.9.3 할당기 요구사항과 목표

- 임의의 요청 순서 처리하기
- 요청에 즉시 응답하기
- 힙만 사용하기
- 블록 정렬하기(정렬 요건)
- 할당된 블록을 수정하지 않기.

### 할당기가 힙을 얼마나 효율적으로 사용하는가를 규정하는 많은 방법

```
1. n개의 할당과 반환 요청의 배열이 주어짐

2. 만일 어떤 응용이 p 바이트 블록을 요청하면, 할당된 블록은 데이터 p 바이트를 가짐

3. 요청 Rk가 완료된 후 종합 데이터 Pk는 현재 할당된 블록들의 데이터들의 합이며, Hk는 현재 (단조 증가하는) 힙의 크기를 나타냄
```

## 9.9.6 묵시적 가용 리스트

- 모든 실용적인 할당기는 블록 경계를 구분하고, 할당된 블록과 가용 블록을 구분하는 데이터 구조를 필요로 함
- 대부분의 할당기는 이 정보를 블록 내에 저장

```

할당기는 간접적으로 가용 블록 전체 집합을 힙 내의 전체 블록을 다니면서 방문할 수 있음
어떤 특별히 표시한 마지막 블록이 필요함
```


## 9.9.12 종합설계 : 간단한 할당기의 구현

### 묵시적 가용 리스트

```
첫번째 워드 : 더블 워드 경계로 정렬된 미사용 패딩 워드
패딩 워드가 필요한 이유 :
header : 4byte
payload 시작 (malloc이 반환하는 건 payload_pointer이다.) -> 즉 사용자가 쓰는 주소 : payload
payload 정렬이 맞지가 않으면 : double 저장 -> 깨질 수 있고, CPU access가 비효율적

패딩 다음에는 특별한 prolog 블록 (헤더와 푸터로만 구성된 8바이트 할당 블록)
프롤로그 블록은 초기화 과정에서 생성되며 절대 반환하지 않음.
프롤로그 블록 다음엔 malloc 또는 free를 호출해서 생성된 0 또는 1개 이상의 일반 블록들이 옴
힙은 항상 특별한 에필로그 블록으로 끝나며, 이것은 헤더만으로 구성된 크기가 0으로 할당된 블록
```

### 명시적 가용 리스트

```
가용 영역에 (free) 포인터 pred와 succ를 포함 시켜 이중 연결 가용 리스트로 구성하는 것

1. 리스트를 새롭게 반환한 블록들을 리스트의 시작 부분에 삽입해서 후입선출 순으로 유지하는 것
(최근에 사용된 블록들을 먼저 조사)

2. 리스트를 주소 순으로 관리하는 것 (리스트 내 각 블럭의 주소가 다음 블럭의 주소보다 작다.)
-> 주소 순서를 사용하는 first fit이 LIFO 순서를 사용하는 경우보다 best fit의 이용도에 근접하는 더 좋은 메모리 이용도를 가짐

단점
일반적으로 가용 블록들이 충분히 커서 모든 필요한 포인터 뿐만 아니라, 헤더 추가적으로 풋터까지 포함해야 한다는 점
그 결과, 최소 블록 크기가 커지고 잠재적인 내부 단편화 가능성이 증가함!!
```

### 분리 가용 리스트

```
기본적인 아이디어 : 모든 가능한 블록 크기를 크기 클래스 size class라고 하는 동일 클래스의 집합들로 분리하는 것
크기 클래스를 정의하는 많은 방법들이 존재함. (예를 들어 블록 크기를 2의 제곱으로 나눌 수도 있음)

간단한 분리 저장장치
각 크기 클래스를 위한 가용 리스트는 간단한 분리 저장장치로 동일한 크기의 블록들을 가지며, 각각은 크기 클래스의 가장 큰 원소의 크기를 가짐
어떤 주어진 크기의 블록을 할당하기 위해 적절한 가용 리스트 검색
만일 리스트가 비어 있지 않다면, 첫 번째 블록 전체를 할당
가용 블록들은 할당 요청을 만족시키기 위해 절대로 분할하지 않음.
만일 리스트가 비어있다면, 할당기는 운영체제로 부터 추가적인 고정 크기의 메모리를 요청하고(대개 여러 개의 페이지 크기로), 이를 동일한 크기의 블록들로 나누며,
블록들을 함께 연결해 새로운 가용 리스트를 만듬
할당기는 블록을 반환할 때 단순히 이 블록을 해당 가용 리스트의 맨 앞에 삽입

분리 맞춤
할당기는 가용 리스트의 배열을 관리
각 가용 리스트는 크기 size 클래스에 연관되며, 일종의 명시적 또는 묵시적 리스트로 구성됨.
각 리스트는 잠재적으로 서로 다른 크기의 블록들을 포함하고 있으며, 이들의 크기는 해당 크기 클래스에 포함됨
```

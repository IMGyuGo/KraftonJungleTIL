## TCP

- 전화기와 비슷한 방식으로 동작
- 3 way handshaking
  - SYN
  - SYN + ACK
  - ACK
- connection에 overhead가 심하고
- 왔다갔다 하면서 뭔갈 많이 물어봄

## UDP

- 비디오 스트리밍, 게임 스트리밍
- 연결이 되었는지 확인 안하고 무조건 전송
- 값이 유실될 가능성이 많음

```

(연결이 되고 계속 데이터를 주고 받으면 연결 오버헤드가 줄어듬)

여러 도메인을 지원할 수 없었는데,

이것을 해결하기 위해 호스트 헤더를 만들었다.
(여러 도메인을 지원할 수 있도록) -> 한 서버가 2개를 받을 수 있도록
```

## HTTP 2.0 시대

```
최근까지도 2.0 많이 지원안한다. (서버 바꾸는 게 비용이 많이 큼)

- Multiplexing (한 연결에 여러 스트리밍을 만들어놔서 거기에만 데이터를 보내고 요청)
- 이미지 5개 요청했으면
    - 이미지 한개를 다시 쪼개서
        - 이미지 1,2,3,4,5를 한 청크로 (512Byte)를 한번에 보냄
        - 서버에서 이미지 각각을 조금씩 보내줌

주요 특징
- 멀티 플렉싱
- 헤더 압축
- 스트림 기반 통신
```

# CGI (Common Gateway Interface)

- 클라이언트쪽은 안 바꾸고 서버쪽에
- CGI요청이 오면, 프로그램을 실행하게 됨
- 프로그램을 stdout으로 받은 것을 무조건 클라이언트에게 전송
- `(동적 웹페이징이 가능해진 계기)`
- 97년 웹 혁명의 시대가 생김 (앱 -> 웹으로 변혁)
- CGI로 100만건의 요청이 들어온다고 가정
  - 100만개의 프로세서의 실행파일이 실행이됨
  - 이걸 버틸만한 웹서버가 없음
  - FastCGI가 출시됨

## FastCGI

- Thread (쓰레드)
  - 웹서버한테 CGI 요청은 똑같음
  - 쓰레드를 실행 [아무 exe를 실행하는 게 아니고 미리 fastcgi 서버의 실행파일만 실행(미리실행)]
  - Flask, Tomcat, web server 전부다 이렇게 작동
- 리소스가 작으면 당연히 죽을 수 있지만, 서버가 죽는거를 방지 가능

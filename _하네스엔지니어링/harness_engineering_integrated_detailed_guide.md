
# 하네스 엔지니어링 통합 정리
## ECC / Toss Harness / 위키독스 하네스 엔지니어링 글을 함께 엮어서 보는 실전 가이드

- 작성 목적:
  - 하네스 엔지니어링 관련 글들을 각각 따로 읽으면 용어는 많은데 구조가 머릿속에 잘 안 잡힘
  - 그래서 이 문서는 세 글을 하나의 큰 그림으로 묶어,
    1) 공통 메시지,
    2) 서로의 차이,
    3) 실전 도입 시 필요한 구조,
    4) 실제 프로젝트에 어떻게 폴더를 채워 나가야 하는지
    까지 한 번에 이해할 수 있도록 정리한 문서다.

- 함께 참고한 글:
  - ECC 리뷰/분석 글
  - Toss Tech의 Harness 관련 글
  - 위키독스의 하네스 엔지니어링 정리 글

---

# 0. 먼저 결론부터

세 글의 공통 메시지는 거의 같다.

> AI의 성능 차이는 모델 자체보다,
> 그 모델을 어떤 규칙/도구/검증/문맥/워크플로우로 감싸는가에서 크게 갈린다.

즉:

- 좋은 모델을 쓰는 것만으로는 부족하다.
- 팀의 규칙, 문맥, 검증 루프, 저장 구조, 실행 환경이 함께 있어야 한다.
- 개인이 “프롬프트 잘 치는 법”을 아는 수준에서 끝나면 조직 생산성은 들쭉날쭉하다.
- 그래서 조직은 AI 사용법이 아니라 **AI가 일하게 되는 시스템**을 설계해야 한다.

이게 바로 하네스 엔지니어링의 핵심이다.

---

# 1. 하네스(harness)란 무엇인가

## 1-1. 비유로 이해하기
하네스는 원래 말에게 씌우는 ‘마구’다.
말이 아무리 힘이 좋아도 마구가 없으면 방향을 못 잡고, 힘을 원하는 곳에 전달하기 어렵다.

AI도 똑같다.

- 모델 = 말의 힘
- 하네스 = 그 힘을 실제 일로 바꾸는 구조

즉 모델만 있으면 “똑똑한 텍스트 생성기”일 뿐이고,
하네스가 있어야 비로소 “일하는 에이전트”가 된다.

## 1-2. 식으로 보면
많은 글에서 반복되는 공식은 이거다.

```text
Agent = Model + Harness
```

여기서 하네스는 다음을 포함한다.

- 시스템 프롬프트
- 도구 정의
- 파일 시스템
- 샌드박스
- 메모리
- 훅
- 검증 루프
- 규칙 집합
- 오케스트레이션 로직
- 문맥 관리 방식

즉, 모델을 제외한 “에이전트 운영에 필요한 나머지 대부분”이 하네스다.

# 2. 세 글을 한 문장으로 요약하면

## 2-1. ECC 글
ECC 글은 하네스를 **실제로 설치 가능한 에이전트 셋업** 관점에서 설명한다.

핵심 질문:
- “혼자서 팀처럼 개발하려면 어떤 구성요소가 필요한가?”
- “Agent / Skill / Hook / Rule / Security를 어떻게 패키징할 것인가?”

즉,
**구체적인 조립 부품**에 가깝다.

## 2-2. Toss 글
Toss 글은 하네스를 **조직 차원의 생산성 시스템** 관점에서 본다.

핵심 질문:
- “왜 같은 모델을 써도 팀원마다 결과가 다를까?”
- “그 차이를 개인 역량이 아니라 팀 시스템으로 흡수할 수 없을까?”
- “플러그인/마켓플레이스/레이어 구조로 저점을 높일 수 없을까?”

즉,
**팀 단위 운영체계**에 가깝다.

## 2-3. 위키독스 글
위키독스 글은 여러 사례를 묶어
**하네스 엔지니어링의 본질과 실전 원칙**을 설명한다.

핵심 질문:
- “모델만으로는 왜 안 되는가?”
- “하네스는 왜 성능의 핵심 변수인가?”
- “실제로 잘 작동하는 하네스는 어떤 원칙을 따르는가?”
- “미래에는 하네스가 서비스 템플릿처럼 될 수 있는가?”

즉,
**개념적 정리 + 실전 원칙 + 미래 전망**에 가깝다.

# 3. 세 글의 공통 핵심

세 글은 표현만 다르고 아래 6가지를 공통으로 말한다.

## 3-1. 개인의 센스에 맡기면 조직 생산성이 흔들린다
같은 모델, 같은 IDE, 같은 저장소를 써도
누군가는 10분 만에 끝내고, 누군가는 1시간 동안 수정 루프를 돈다.

이 차이는 흔히 “개인 프롬프트 실력 차이”처럼 보이지만,
세 글은 그걸 개인 문제가 아니라 **시스템 문제**로 본다.

즉:
- 잘하는 사람이 잘하는 이유를 개인 비법으로 남기지 말고
- 재사용 가능한 구조로 만들어
- 팀에 배포해야 한다

## 3-2. 문서는 정적이지만, 하네스는 실행된다
일반 문서는 “읽는 자료”다.
하지만 하네스 안의 규칙/플러그인/훅/스킬은 “행동을 바꾸는 구조”다.

예:
- 팀 브랜치 전략이 문서에만 있으면 안 지킬 수도 있다
- 하네스 훅에 들어가 있으면 AI가 main에서 커밋하려 할 때 feature 브랜치로 유도할 수 있다

즉,
하네스는 “설명서”가 아니라 “행동 교정 장치”다.

## 3-3. 중요한 것은 더 많은 문맥이 아니라 더 좋은 문맥이다
문맥을 마구 많이 넣는다고 좋은 게 아니다.
오히려 컨텍스트가 길어질수록 모델 추론 능력이 떨어지고,
관련 없는 출력이 쌓이면 문맥이 썩는다.

핵심은:
- 필요한 정보만
- 필요한 시점에
- 필요한 범위로
주입하는 것이다.

## 3-4. 도구를 많이 붙이는 게 능사가 아니다
MCP나 각종 서버를 과도하게 연결하면
설명문 자체가 컨텍스트 예산을 잡아먹는다.

그래서 실전에서는 자주 이런 선택이 더 좋다.

- 가능한 건 기존 CLI 활용
- 무거운 MCP는 꼭 필요한 것만
- 로컬 도구/스크립트로 대체 가능한 건 대체

## 3-5. 검증 루프가 없으면 에이전트는 쉽게 멈추거나 착각한다
AI는 종종:
- 다 안 했는데 다 했다고 말하거나
- 일부만 고쳐놓고 끝났다고 하거나
- 컴파일도 안 되는 상태에서 완료라 말한다

그래서 다음이 필요하다.

- 타입체크
- 테스트
- 포매터
- 브라우저 E2E
- lint
- coverage
- 정책 검사

즉,
“생성”보다 “자기검증”이 더 중요해지는 순간이 온다.

## 3-6. 엔지니어 역할이 바뀐다
예전엔 코드를 직접 잘 짜는 것이 핵심이었다면,
이제는 AI가 올바르게 일하도록:

- 환경을 설계하고
- 규칙을 정하고
- 실패를 재발 방지 구조로 바꾸고
- 검증 루프를 걸고
- 문맥을 계층화하고
- 팀에 배포하는 능력

이 중요해진다.

# 4. ECC, Toss, 위키독스의 차이를 구조적으로 비교

| 항목 | ECC 글 | Toss 글 | 위키독스 글 |
|---|---|---|---|
| 초점 | 실전 셋업 부품 | 조직 생산성 시스템 | 원칙/개념/미래 |
| 핵심 단위 | Agent, Skill, Hook, Rule | Plugin, Workflow, Marketplace, Layer | Harness 구성요소 전반 |
| 질문 | 어떻게 설치/구성할까 | 어떻게 조직에 배포할까 | 왜 이게 핵심인가 |
| 강점 | 바로 조립 가능한 감각 | 팀 운영 관점이 강함 | 큰 그림을 가장 잘 잡아줌 |
| 읽는 느낌 | “도구 상자” | “조직 설계 문서” | “개념 지도” |

정리하면:

- ECC는 **부품 설명서**
- Toss는 **조직 운영 전략**
- 위키독스는 **철학 + 실전 원칙 + 전망**

# 5. ECC를 다시 풀어서 이해하기

ECC 글은 처음 보면 용어가 많아 복잡해 보이는데,
사실 아래처럼 보면 훨씬 단순해진다.

## 5-1. Agent
역할을 가진 작업 단위다.

예:
- planner
- code-reviewer
- security-reviewer
- backend-implementer
- docs-writer

중요한 점:
Agent는 “사람 역할 이름”처럼 보이지만,
실제로는 **제한된 책임 + 제한된 도구 + 제한된 문맥**을 가진 실행 프로필에 가깝다.

## 5-2. Skill
반복 가능한 작업 절차를 묶은 것이다.

예:
- TDD로 기능 구현하기
- 코드리뷰 수행하기
- 보안 점검하기
- 레거시 함수 리팩토링하기
- 릴리즈 체크리스트 수행하기

즉 Skill은
“무엇을 할 수 있나”보다
“어떻게 그 일을 수행하나”에 가깝다.

## 5-3. Command
슬래시 커맨드 같은 진입점이다.

예:
- /plan
- /tdd
- /code-review
- /evolve

Command는 사용자가 AI 시스템을 호출하는
**짧은 UX 엔트리포인트** 역할을 한다.

## 5-4. Hook
특정 시점에 자동으로 실행되는 스크립트/검사다.

예:
- 도구 사용 전 검사
- 도구 사용 후 정리
- 세션 시작 시 context 로딩
- compact 전에 진행상황 저장
- 종료 시 학습 상태 저장

Hook이 중요한 이유는
사람이 일일이 “이제 검사해”, “이제 저장해”, “이제 정리해”라고 말하지 않아도
시스템이 알아서 개입하기 때문이다.

## 5-5. Rule
반드시 지켜야 하는 규칙이다.

예:
- 테스트 없이 머지 금지
- main 브랜치 직접 작업 금지
- console.log 금지
- 특정 디렉터리 구조 준수
- 보안 관련 파일 접근 제한

Rule은 “권장사항”이 아니라
에이전트를 특정 방향으로 정렬하는 기준이다.

## 5-6. Security / AgentShield
에이전트 설정 자체를 스캔하는 보안 계층이다.

이 부분이 중요한 이유는,
우리는 보통 “AI가 만든 코드 보안”만 생각하는데
ECC는 그보다 앞 단계인 **에이전트 운영 설정의 취약점**도 문제로 본다.

예:
- 시크릿 노출
- 과도한 권한
- 훅 인젝션
- 위험한 MCP 설정
- 잘못된 에이전트 설정

즉,
“AI가 무엇을 만들었는가”뿐 아니라
“AI가 어떤 환경과 권한으로 일하고 있는가”도 보겠다는 뜻이다.

## 5-7. Instinct
관찰된 작업 패턴을 학습 자산으로 축적하는 개념이다.

쉽게 말하면:
- 자주 반복되는 좋은 패턴을 저장하고
- 나중에 그것을 새로운 Skill/Command/Agent로 발전시키는 구조다.

즉,
즉흥적인 잘한 행동을
구조화된 재사용 자산으로 승격하는 장치다.

# 6. Toss 글을 다시 풀어서 이해하기

Toss 글은 ECC보다 더 조직 관점이다.

## 6-1. 왜 같은 LLM을 써도 팀 성과가 다를까
Toss 글의 출발점은 아주 현실적이다.

- 같은 모델을 쓴다
- 같은 IDE를 쓴다
- 같은 저장소에서 일한다

그런데 결과물 품질은 크게 갈린다.

이 차이는 모델 차이가 아니라
“작업 전에 어떤 맥락을 설계해 넣느냐”의 차이로 설명된다.

즉,
개인의 LLM Literacy가 팀 전체 생산성 편차를 만든다.

## 6-2. Raising the Floor
여기서 Toss가 강조하는 건
평균을 높이는 것보다 **저점을 높이는 것**이다.

왜냐하면 조직 생산성은 종종 최고의 사람보다
“평균 이하 케이스가 얼마나 덜 망하느냐”에 의해 좌우되기 때문이다.

그래서:
- 잘하는 한 사람의 감각을
- 플러그인/워크플로우/명령으로 패키징해서
- 다른 사람도 같은 수준의 과정을 밟게 해야 한다

이 발상이 중요하다.

## 6-3. Executable SSOT
문서를 SSOT로 두면 곧 낡는다.
하지만 플러그인/하네스가 SSOT가 되면 실행할 수 있다.

예:
- 사람이 보면 업무 가이드
- AI가 보면 시스템 프롬프트
- 코드가 바뀌면 즉시 반영
- 규칙이 바뀌면 팀 전체가 바로 새 행동을 따름

즉 SSOT가 “읽는 문서”에서 “실행되는 구조”로 바뀌는 것이다.

## 6-4. Marketplace
Toss는 마켓플레이스/플러그인 배포를 중요하게 본다.

이건 단순히 공유 저장소를 뜻하는 게 아니라,
**조직의 워크플로우를 배포하는 플랫폼**이라는 의미가 있다.

예:
- 브랜치 전략 플러그인
- Jira 이슈 생성 워크플로우
- 코드리뷰 규칙 플러그인
- 신규 기능 생성 슬래시 커맨드

즉,
지식 공유가 아니라
**일하는 방식 자체를 설치 가능한 형태로 만든다**는 관점이다.

## 6-5. Layered Architecture
Toss가 제안하는 계층화는 매우 중요하다.

### Global Layer
전사 공통 정책
- 보안
- 기본 코딩 스타일
- 공통 커밋/브랜치 룰
- 개인정보/민감정보 처리 규칙

### Domain Layer
팀/비즈니스 도메인 규칙
- 결제 팀 규칙
- 정산 도메인 규칙
- 회원 도메인 용어
- 팀별 승인 프로세스

### Local Layer
레포지토리/프로젝트 고유 규칙
- 특정 디렉터리 구조
- 현재 프로젝트 구현 방식
- 레거시 제약
- 실제 테스트 명령어
- 프로젝트별 주의사항

이 계층화가 중요한 이유:
모든 지식을 한 파일에 때려넣으면 관리가 불가능해지기 때문이다.

# 7. 위키독스 글에서 특히 중요한 부분
## 7-1. 하네스 엔지니어링 실전 원칙

사용자가 중요하게 본 부분이기도 하므로,
여기는 더 천천히 풀어본다.

## 원칙 1. 실패에서 시작하라
가장 중요한 원칙이다.

많은 사람이 처음부터 “완벽한 하네스 구조”를 설계하려 한다.
하지만 위키독스 글은 반대로 말한다.

- 이상적인 구조를 상상해서 한 번에 만들려 하지 말고
- 에이전트가 실제로 실패한 지점을 관찰하고
- 그 실패가 다시 발생하지 않도록 구조를 추가하라

이 방식이 좋은 이유:
- 실제 문제를 기준으로 개선하므로 과설계가 줄어든다
- 팀의 현실에 맞는 가드레일만 쌓이게 된다
- 문서가 아니라 실패 로그가 설계의 출발점이 된다

### 실전 예시
AI가 main 브랜치에서 바로 커밋했다.
그럼 문서에 “하지 마세요”를 쓰는 게 아니라,
다음부터는 Hook으로 감지해 feature 브랜치 생성 로직을 넣는다.

AI가 테스트 없이 완료라고 했다.
그럼 “테스트도 해주세요”라고 말만 바꾸는 게 아니라,
완료 전에 테스트 실행을 강제하는 back-pressure를 넣는다.

즉:
- 실패
- 재현
- 구조화
- 재발 방지

이 루프가 핵심이다.

## 원칙 2. 적게 넣어라
처음 하네스를 설계할 때 흔히 하는 실수가 있다.

- 프로젝트 개요
- 디렉터리 전체 설명
- 온갖 운영 규칙
- 모든 팀 문서 요약
- 장문의 아키텍처 설명

이걸 한꺼번에 넣는 것이다.

문제는:
이게 많을수록 AI가 더 똑똑해지는 게 아니라,
오히려 중요한 것과 덜 중요한 것이 섞여서 판단력이 흐려진다.

실전적으로는:
- 보편적으로 항상 필요한 규칙
- 반드시 지켜야 하는 정책
- 현재 작업에 직접 필요한 정보
이 정도만 먼저 넣는 편이 낫다.

### 핵심 오해
“더 많은 컨텍스트 = 더 좋은 결과”
가 아니다.

실제로는
“더 선별된 컨텍스트 = 더 안정된 결과”
에 가깝다.

## 원칙 3. 도구를 과하게 연결하지 마라
도구가 많으면 좋아 보인다.
하지만 실제로는:

- 도구 설명이 길어진다
- 시스템 프롬프트가 비대해진다
- 선택지가 너무 많아져서 판단 비용이 올라간다
- 쓸데없는 호출이 늘어난다

그래서 실전에서는:
- 이미 CLI로 되는 건 CLI 우선
- 무거운 도구는 꼭 필요한 것만
- 자주 쓰는 흐름만 경량 래퍼로 만들기
- 도구 추가보다 도구 제거가 더 중요할 때가 많다

## 원칙 4. 점진적 작업을 강제하라
이건 실제로 매우 중요하다.

AI는 큰 일을 한 번에 맡기면
- 중간에 문맥을 잃거나
- 절반만 하고 끝냈다고 하거나
- 부분 구현을 전체 완성처럼 착각하기 쉽다

그래서 다음이 필요하다.

- 작업 단위를 작게 쪼갠다
- 한 번에 하나씩 하게 한다
- 끝날 때마다 커밋/노트/상태 기록을 남긴다
- 다음 세션이 기록을 읽고 이어가게 한다

즉, AI에게도 “작업 분할 + 인수인계 문화”가 필요하다.

## 원칙 5. 자기검증을 강제하라
생성만 잘하면 되는 게 아니다.
검증 없는 생성은 늘 불안정하다.

실전적 하네스는 보통 이렇게 묻는다.

- 컴파일 되나?
- 테스트 통과하나?
- 타입 에러 없나?
- 브라우저에서 실제로 동작하나?
- 린트 규칙 맞나?
- 정책 위반 없나?

AI가 “끝났어요”라고 말하는 건 아무 의미가 없다.
시스템이 “끝났다고 인정하는 조건”을 별도로 가져야 한다.

# 8. 위키독스 글의 두 번째 핵심
## 미래: 하네스는 새로운 서비스 템플릿이 될 것인가

이 부분은 단순 전망이 아니라,
실제로 앞으로 조직이 어떻게 움직일지를 생각하게 만드는 포인트다.

핵심 아이디어는 이렇다.

> 대부분의 조직은 앱마다 완전히 다른 세상을 사는 것이 아니다.
> 주요 기술 스택과 서비스 유형은 어느 정도 반복된다.
> 그렇다면 애플리케이션 유형별 하네스를 템플릿처럼 미리 갖출 수 있지 않을까?

이 말은 아주 중요하다.

예전의 템플릿:
- Spring Boot 초기 프로젝트 템플릿
- Next.js 스타터
- 사내 백엔드 골든 패스
- CI/CD 기본 템플릿

미래의 템플릿:
- “AI가 이 프로젝트에서 일하는 방식”까지 포함된 템플릿

즉,
단순 코드 뼈대가 아니라
아래까지 포함한 템플릿이 된다.

- 글로벌 규칙
- 도메인 규칙
- 로컬 룰
- 도구 셋
- 훅
- 검증 루프
- 진행 기록 파일
- 슬래시 커맨드
- 역할별 에이전트
- 기본 워크플로우
- 보안 검사
- 컨텍스트 계층화 방식

즉 “프로젝트 스타터”가 아니라
**“AI가 안전하고 일관되게 일할 수 있는 스타터”**가 된다.

## 왜 이게 중요한가
이렇게 되면 기술 선택 기준도 달라진다.

예전:
- 개발자 경험이 좋은가
- 라이브러리 생태계가 풍부한가
- 커뮤니티가 큰가

앞으로:
- AI가 다루기 쉬운 구조인가
- 좋은 하네스를 얹기 쉬운가
- 규칙과 검증을 시스템화하기 쉬운가
- 지식 계층화가 쉬운가
- 자동화 플러그인을 배포하기 쉬운가

즉,
AI 친화성(AI-readiness)이 기술 선택 기준으로 올라올 수 있다.

## 또 다른 중요한 포인트
위키독스 글은 레거시 코드베이스와 AI-native 코드베이스의 격차도 시사한다.

새 코드베이스는 처음부터
- 규칙
- 검증
- 파일 구조
- 상태 기록
- 하네스
를 함께 설계할 수 있다.

하지만 레거시는
- 암묵지가 많고
- 구조가 흐리고
- 경고가 너무 많고
- 문서와 코드가 어긋나서
하네스를 나중에 덧대기가 어렵다.

이건 아주 현실적인 문제다.

즉,
하네스는 나중에 붙이는 장식이 아니라
가능하면 프로젝트 초반부터 설계에 포함시키는 것이 좋다.

# 9. 그래서 실제 도입 시 무엇을 설계해야 하는가

여기서부터가 가장 실전적인 부분이다.

하네스를 도입할 때 많은 사람이
“에이전트를 몇 개 만들지?”
“프롬프트 파일은 어디 둘지?”
부터 고민한다.

그런데 실제로는 아래 순서가 더 중요하다.

## 9-1. 먼저 정해야 할 7가지

### 1) 금지해야 할 실패는 무엇인가
예:
- main 브랜치 직접 수정
- 테스트 없이 완료 처리
- 민감 정보 로그 출력
- 프로젝트 규칙 위반
- 디렉터리 구조 파괴
- 레거시 핵심 파일 무단 변경

### 2) 반복해서 잘하고 싶은 작업은 무엇인가
예:
- 신규 기능 생성
- 버그 수정
- 코드 리뷰
- 테스트 보강
- 문서화
- 릴리즈 전 점검

### 3) 어떤 검증을 자동화할 것인가
예:
- lint
- typecheck
- unit test
- integration test
- e2e
- security scan
- format

### 4) 문맥을 어떻게 계층화할 것인가
예:
- 글로벌 규칙
- 도메인 규칙
- 프로젝트 규칙
- 현재 작업 상태

### 5) 어떤 것은 사람이 승인해야 하는가
예:
- 데이터베이스 스키마 변경
- 운영 배포
- 보안 관련 설정 변경
- 결제/정산 핵심 로직 수정

### 6) 세션 간 상태를 어디에 남길 것인가
예:
- progress.md
- task-log.md
- decision-log.md
- current-plan.md

### 7) 실패를 어떻게 학습 자산으로 승격할 것인가
예:
- 동일 실패가 3번 나오면 Rule로 승격
- 자주 반복되는 성공 작업은 Skill로 승격
- 자주 쓰는 진입 흐름은 Command로 승격

# 12. 이 예시에서 각 파일이 실제로 무슨 역할을 하나

## 12-1. .ai/rules/00-global-c-style.md
내용 예시:
- 함수 길이 제한
- 에러 처리 패턴 통일
- 매직넘버 금지
- 헤더/구현 분리 원칙
- 메모리 해제 책임 명시

이 파일은 “모든 C 파일에 공통 적용되는 룰”이다.

## 12-2. .ai/rules/10-domain-sql-parser.md
내용 예시:
- INSERT와 SELECT는 prepare 단계에서 먼저 구분
- validation은 parsing 직후 수행
- meta command와 SQL 문장은 서로 다른 경로로 처리
- 파서가 실행 로직을 직접 수행하지 않음

이 파일은 “도메인 규칙”이다.
즉 SQL 처리기라는 프로젝트 성격에서 나오는 규율이다.

## 12-3. .ai/rules/11-domain-storage-format.md
내용 예시:
- Row 직렬화 포맷은 문서(row-format.md)와 항상 일치
- 포맷 변경 시 반드시 regression test 추가
- deserialize는 boundary check 포함
- 저장 포맷 깨지는 변경은 ADR 남기기

이건 “파일 저장 포맷 관련 안전장치”다.

## 12-4. .ai/skills/implement-parser-safely.md
내용 예시:
- 기존 parser 테스트 확인
- 새 문법 추가 전 grammar 문서 갱신
- 파서 수정
- 에러 케이스 테스트 추가
- 정상 케이스 테스트 추가
- build/test 실행
- progress 기록

즉, 특정 작업을 수행하는 절차를 템플릿화한 것이다.

## 12-5. .ai/hooks/before-complete.sh
내용 예시:
- build 성공 여부 검사
- tests 통과 여부 검사
- regression test 검사
- progress.md 갱신 여부 검사

이 훅은 AI가 “끝났습니다”라고 말하기 직전에 개입하는 가드레일이다.

## 12-6. .ai/state/progress.md
내용 예시:
- 현재 단계: 5단계 INSERT validation
- 완료된 것
- 남은 것
- 막힌 이슈
- 다음 세션 시작 시 읽을 내용

이 파일이 중요한 이유:
세션이 바뀌어도 작업 맥락이 유지되기 때문이다.

# 13. 실제 작업 흐름은 어떻게 흘러가나

## 시나리오: “INSERT 유효성 검사 추가”
사용자는 다음처럼 요청한다고 가정한다.

> username 길이와 email 길이 검사를 넣어줘

하네스가 없는 경우:
- AI가 statement.c 아무데나 막 수정
- 테스트 안 짬
- 에러 메시지 형식 통일 안 됨
- progress 기록 안 남김
- 다음 세션에서 왜 이렇게 바뀌었는지 모름

하네스가 있는 경우:
1. `/new-sql-feature` 또는 관련 skill 실행
2. parser-agent가 현재 parser 규칙 파일 확인
3. domain rule에서 validation 위치 확인
4. 구현 전 grammar/decision 문서 확인
5. 코드 수정
6. regression test 생성
7. build/test 실행
8. before-complete 훅이 검증
9. progress.md와 handoff.md 갱신
10. review-agent가 스타일/안전성 재확인

즉,
작업 하나가 “명령 → 규칙 → 구현 → 검증 → 기록”의 체인으로 바뀐다.

# 14. SQL Processor 말고, 웹 프로젝트라면 어떻게 달라질까

예시: Virtual DOM 학습/데모 프로젝트

```text
virtual-dom-demo/
├─ .ai/
│  ├─ agents/
│  │  ├─ runtime-agent.md
│  │  ├─ diff-agent.md
│  │  ├─ demo-agent.md
│  │  └─ docs-agent.md
│  ├─ skills/
│  │  ├─ add-vdom-feature.md
│  │  ├─ implement-hook-step.md
│  │  ├─ add-demo-log-ui.md
│  │  └─ write-blog-summary.md
│  ├─ rules/
│  │  ├─ 00-global-js-style.md
│  │  ├─ 10-domain-vdom-principles.md
│  │  ├─ 11-domain-diff-rules.md
│  │  └─ 20-local-demo-constraints.md
│  ├─ hooks/
│  │  ├─ before-complete.sh
│  │  ├─ after-edit.sh
│  │  └─ session-start.sh
│  ├─ state/
│  │  ├─ progress.md
│  │  ├─ current-step.md
│  │  └─ patch-log.md
│  └─ checks/
│     ├─ test.sh
│     ├─ demo-smoke.sh
│     └─ lint.sh
├─ src/
├─ demo/
├─ tests/
└─ README.md
```

이 프로젝트에서 domain rule 예시:
- 서로 다른 element type이면 subtree 교체
- text node는 value 비교
- props diff와 event diff를 분리
- hooks는 top-level component에서만 사용
- 데모 패널의 patch log는 항상 유지

즉, 프로젝트가 바뀌면 규칙 내용과 검증 내용이 바뀐다.
하지만 큰 구조는 그대로 재사용할 수 있다.

이게 바로 “하네스가 템플릿이 된다”는 말의 실제 의미다.

# 15. 그래서 무엇부터 만들면 되는가
## 가장 현실적인 1주차 도입 계획

처음부터 ECC 전체처럼 거대하게 만들 필요 없다.
아래 순서가 현실적이다.

## 1단계. Rules부터 만든다
최소 3개면 된다.

```text
.ai/rules/
├─ 00-global.md
├─ 10-domain.md
└─ 20-local.md
```

이유:
하네스의 핵심은 결국 “무엇을 지키게 할 것인가”이기 때문이다.

## 2단계. State 파일 2개 만든다
```text
.ai/state/
├─ progress.md
└─ handoff.md
```

이유:
세션 넘어갈 때 문맥이 끊기는 문제를 막기 위해서다.

## 3단계. Check 스크립트 2개 만든다
```text
.ai/checks/
├─ build.sh
└─ test.sh
```

이유:
검증 없는 하네스는 껍데기이기 때문이다.

## 4단계. Skill 2개 만든다
예:
- implement-feature.md
- fix-bug.md

이유:
반복 작업을 표준화해야 하기 때문이다.

## 5단계. Hook 1개만 둔다
예:
- before-complete.sh

이유:
“완료” 선언 전에 검증을 넣는 것만으로도 효과가 크다.

# 16. 실전에서 자주 하는 오해

## 오해 1. 에이전트를 많이 만들수록 좋다
아니다.
역할 분리는 멋있어 보이지만,
실전에서는 너무 많은 에이전트가 오히려 복잡성만 키운다.

처음엔:
- planner
- implementer
- reviewer
정도면 충분하다.

## 오해 2. 모든 문서를 다 넣어야 한다
아니다.
문맥 과부하는 오히려 성능을 떨어뜨린다.

처음엔:
- 항상 필요한 규칙
- 현재 작업에 직접 필요한 문서
- 최근 진행 상태
이 정도만 주는 게 낫다.

## 오해 3. RAG를 붙이면 다 해결된다
아니다.
RAG는 지식 검색에 강하지만,
행동 규율과 워크플로우 강제는 별개의 문제다.

검색 시스템과
실행/정렬 시스템은 구분해서 생각해야 한다.

## 오해 4. 프롬프트만 잘 쓰면 된다
아니다.
하네스는 프롬프트보다 넓다.

프롬프트는 일부일 뿐이고,
실제로는:
- 파일 구조
- 상태 저장
- 훅
- 도구 제약
- 테스트
- 승인 지점
- 워크플로우
가 훨씬 중요해진다.

# 17. 세 글을 종합한 최종 프레임워크
## 머릿속에 이렇게 넣으면 된다

하네스 설계를 아래 5층으로 생각하면 정리가 쉽다.

## 층 1. 규칙층
무엇을 반드시 지켜야 하는가

- 보안
- 스타일
- 브랜치 전략
- 테스트 정책
- 도메인 제약

## 층 2. 문맥층
무슨 지식을 언제 넣을 것인가

- global
- domain
- local
- current task
- session state

## 층 3. 실행층
어떻게 일하게 할 것인가

- agent
- skill
- command
- workflow

## 층 4. 검증층
어떻게 틀린 걸 잡을 것인가

- lint
- typecheck
- unit test
- e2e
- policy check
- security scan

## 층 5. 학습층
실패와 성공을 어떻게 자산화할 것인가

- progress
- handoff
- known failures
- instinct-like pattern accumulation
- skill 승격
- rule 승격

이 5층이 갖춰지면,
그때부터는 “AI를 쓴다”가 아니라
“AI가 우리 시스템 안에서 일한다”에 가까워진다.

# 18. 사용자 관점에서 가장 중요한 정리

질문의 핵심은 사실 이거다.

> “결국 프로젝트에 도입하려면 어떤 파일을 어떤 철학으로 채워야 하나?”

답은 다음과 같다.

## 먼저 채워야 할 것
1. 규칙 파일
2. 상태 파일
3. 검증 스크립트

## 그 다음 채워야 할 것
4. 반복 작업용 스킬
5. 완료 전 훅
6. 리뷰용 에이전트

## 나중에 붙여야 할 것
7. 서브에이전트
8. 마켓플레이스/공유 구조
9. 자동 학습/Instinct류 구조
10. 도메인 특화 모델/데이터 플라이휠

즉,
가장 먼저 필요한 것은 화려한 에이전트 군단이 아니라

- 규칙
- 상태 기록
- 검증 루프

이다.

이 세 가지가 없는 상태에서 에이전트만 늘리면
복잡한 자동완성 시스템 이상이 되기 어렵다.

# 19. 한 문장 결론

## ECC가 알려준 것
하네스는 구체적인 부품으로 조립할 수 있다.

## Toss가 알려준 것
하네스는 개인 생산성 팁이 아니라 조직 운영 시스템이 될 수 있다.

## 위키독스 글이 알려준 것
하네스는 모델보다 덜 화려하지만, 실제 성능과 재현성을 결정하는 핵심이다.
그리고 앞으로는 서비스 템플릿처럼 프로젝트 시작점에 기본 탑재될 가능성이 높다.

# 20. 바로 실행 가능한 시작안

지금 당장 하나의 프로젝트에 도입하려면,
아래 6개 파일부터 만드는 걸 추천한다.

```text
.ai/rules/00-global.md
.ai/rules/10-domain.md
.ai/rules/20-local.md
.ai/state/progress.md
.ai/checks/test.sh
.ai/hooks/before-complete.sh
```

이 6개만 있어도:
- 무엇을 지켜야 하는지 생기고
- 어디까지 했는지 남길 수 있고
- 끝났다고 말하기 전에 검사할 수 있다

즉, 하네스의 최소 골격이 생긴다.

# 21. 마지막 정리

하네스 엔지니어링은 프롬프트 장인이 되는 기술이 아니다.
그보다는 아래에 가깝다.

- 실패를 구조화하는 기술
- 팀의 암묵지를 실행 가능한 형태로 바꾸는 기술
- AI를 조직 규칙 안에 넣는 기술
- 개인의 감각을 팀 시스템으로 승격하는 기술
- 코드뿐 아니라 작업 방식 자체를 배포하는 기술

그래서 앞으로 중요한 질문은
“어떤 모델을 쓸까?”만이 아니라

- 우리 팀의 규칙은 어디에 저장되는가
- AI는 어떤 조건에서 완료를 선언할 수 있는가
- 문맥은 어떻게 계층화되는가
- 실패는 어떻게 다시는 반복되지 않게 되는가
- 잘한 작업은 어떻게 재사용 가능한 워크플로우가 되는가

가 될 것이다.

이 질문들에 답하기 시작하면,
그때부터 진짜 하네스 설계가 시작된다.

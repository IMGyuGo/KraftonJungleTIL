# 「하네스 엔지니어링 - Everything Claude Code 리뷰」 단계별 해설

원문: 갓대희 블로그의 **“하네스 엔지니어링 - Everything Claude Code 리뷰 : 혼자서 팀처럼 개발하는 에이전트 셋업”** 글을 바탕으로, 처음 보는 개념을 하나씩 풀어서 이해할 수 있도록 재구성한 문서입니다.

---

## 1. 이 글은 대체 무슨 글인가?

이 글은 단순히 “Claude Code 설정법”을 소개하는 글이 아닙니다.
핵심은 다음입니다.

> **AI 코딩 에이전트를 더 잘 쓰기 위해, 에이전트 주변에 규칙/역할/자동화/보안 체계를 묶어 두는 방법**을 설명하는 글입니다.

원문에서 소개하는 대상은 **Everything Claude Code(ECC)** 라는 오픈소스 프로젝트입니다. 글에서는 ECC를 다음처럼 설명합니다.

- 단순한 프롬프트 모음이 아니라,
- **에이전트(roles)**,
- **스킬(workflows)**,
- **명령어(commands)**,
- **훅(hooks)**,
- **규칙(rules)**,
- **보안 스캐너(AgentShield)**

까지 포함한 **에이전트 하네스 성능 최적화 시스템**이라고 정리합니다.

즉, 이 글의 주제는 크게 두 가지입니다.

1. **ECC라는 프로젝트가 무엇인지**
2. **왜 요즘은 AI에게 일을 잘 시키기 위해 하네스(harness) 구조가 중요해지는지**

출처: 블로그 본문 서두와 목차, ECC 소개 부분. citeturn465257view0turn685678view1

## 2. 먼저 알아야 할 가장 큰 개념: 하네스(Harness)

### 2-1. 하네스가 뭔가?

일반적으로 **하네스**는 어떤 시스템이 안정적으로 동작하도록 주변을 잡아주는 “보조 구조”를 뜻합니다.

예를 들면:

- **테스트 하네스**: 테스트 실행 환경을 통제해 주는 틀
- **안전 하네스**: 몸을 묶어서 추락을 막는 장치

원문에서 말하는 **에이전트 하네스(agent harness)** 는 비슷한 발상입니다.

즉:

- AI에게 어떤 입력을 줄지
- 어떤 규칙을 적용할지
- 어떤 도구를 허용할지
- 어떤 작업 전에 검사할지
- 결과를 어떻게 검증할지

를 **바깥 구조로 통제하는 시스템**입니다. 원문은 이를 “프롬프트, 규칙, 훅, 권한 등을 체계적으로 관리하는 외부 프레임워크”라고 설명합니다. citeturn465257view0

### 2-2. 왜 이런 게 필요한가?

AI 코딩 도구를 그냥 쓰면 보통 이런 문제가 생깁니다.

- 세션마다 스타일이 흔들림
- 프로젝트 규칙을 자꾸 잊음
- 위험한 명령을 실행할 수 있음
- 긴 작업에서 컨텍스트가 쉽게 낭비됨
- 비슷한 작업을 반복할 때 매번 처음부터 지시해야 함

그래서 하네스는 AI를 더 “똑똑하게” 만드는 게 아니라,
**AI가 일하는 방식 자체를 구조화**하는 데 목적이 있습니다.

한 줄로 말하면:

> 모델 자체를 바꾸는 게 아니라, **모델을 둘러싼 운영 체계**를 만드는 것.

---

## 3. 이 글의 중심 프로젝트: ECC는 무엇인가?

원문에 따르면 ECC는 **Everything Claude Code**라는 오픈소스 프로젝트이며, 제작자는 **Affaan Mustafa**입니다. 글에서는 GitHub, npm 패키지, MIT 라이선스, 웹사이트, 지원 플랫폼 등을 함께 소개합니다. 또한 Claude Code만이 아니라 Codex, Cursor, OpenCode 등 여러 환경을 함께 다루는 **크로스 하네스 생태계**로 설명합니다. citeturn465257view0turn535231view1

여기서 중요한 포인트는 이름에 “Claude Code”가 들어가더라도,
이 프로젝트의 생각 자체는 훨씬 넓다는 점입니다.

즉 ECC는 이런 질문에 대한 답입니다.

- Claude Code를 더 잘 쓰려면?
- Codex에서도 비슷한 운영 체계를 만들 수 있을까?
- Cursor 같은 IDE 기반 도구에도 비슷한 규칙/훅을 넣을 수 있을까?

이 질문들에 대해,
원문은 **“한 플랫폼만이 아니라 여러 AI 코딩 환경에 공통 운영 체계를 이식하려는 시도”** 로 ECC를 바라봅니다. citeturn535231view1

---

## 4. 글 전체를 한 문장으로 요약하면

이 글은 이렇게 요약할 수 있습니다.

> **혼자 개발하더라도, AI에게 팀처럼 역할을 나누고 규칙을 주고 자동화를 붙이면 생산성을 높일 수 있다. ECC는 그걸 위한 큰 템플릿이다.**

그래서 글 안에는 단순 사용법보다,
다음처럼 “개발 운영 체계”에 가까운 얘기가 많이 나옵니다.

- planner, reviewer 같은 역할 분리
- 작업 흐름을 skills로 패키징
- 작업 전후 훅 자동 실행
- 언어별 규칙 파일
- 보안 스캔
- 병렬 인스턴스 운영
- 세션 패턴 학습

처음 보면 용어가 많은 이유가 바로 이것입니다.
**이 글은 AI 도구 소개글이면서 동시에 ‘AI 팀 운영 방법론’ 소개글**이기 때문입니다.

## 5. 용어를 하나씩 아주 쉽게 풀기

이 부분이 가장 중요합니다. 원문에 등장하는 낯선 개념을 초보 관점에서 다시 설명합니다.

### 5-1. Agent(에이전트)

에이전트는 쉽게 말해 **역할이 정해진 AI 작업자**입니다.

예:

- planner: 계획 세우는 담당
- code-reviewer: 코드 리뷰 담당
- security-reviewer: 보안 점검 담당
- build-error-resolver: 빌드 에러 해결 담당

원문에서는 각 에이전트가 Markdown + YAML frontmatter 형태로 정의되고,
`name`, `description`, `tools`, `model` 같은 정보를 가진다고 설명합니다. citeturn685678view1

#### 왜 필요한가?

하나의 AI에게 모든 역할을 다 맡기면,
질문도 길어지고 컨텍스트도 커지고 행동도 불안정해집니다.

반면 역할을 나누면:

- 무엇을 잘해야 하는지가 분명해지고
- 허용 도구도 줄일 수 있고
- 특정 작업만 맡기기 쉬워집니다.

즉 에이전트는 “또 다른 모델”이 아니라,
**같은 모델을 역할별로 포장한 작업 단위**라고 이해하면 됩니다.

---

### 5-2. Subagent(서브에이전트)

원문은 서브에이전트를 **제한된 범위와 도구 권한을 가진 위임 프로세스**라고 설명합니다. citeturn685678view0

쉽게 말하면:

- 메인 AI가 전체 상황을 보고 있고
- 그중 일부 일을 전문 담당자에게 넘기는 구조입니다.

예:

- 메인 에이전트: “이번 기능 전체 구현해”
- 서브에이전트 A: 설계 검토
- 서브에이전트 B: 테스트 작성
- 서브에이전트 C: 보안 체크

#### 왜 좋은가?

- 메인 컨텍스트를 덜 씀
- 특정 업무를 더 좁게 시킬 수 있음
- 권한도 최소화 가능

즉, **한 명의 만능 비서보다 작은 전문팀을 꾸리는 느낌**입니다.

---

### 5-3. Skill(스킬)

스킬은 **반복 작업 절차를 재사용 가능한 작업 템플릿으로 만든 것**입니다.

원문은 skills를 `~/.claude/skills/`에 저장되는 워크플로우 정의라고 설명합니다. 또한 코드맵(codemap)을 통해 코드베이스를 덜 비싸게 탐색하게 해 준다고 소개합니다. citeturn685678view0

예를 들어 스킬은 이런 느낌입니다.

- “버그 재현 → 원인 찾기 → 테스트 추가 → 수정 → 회귀 테스트”
- “새 기능 설계 → 파일 탐색 → 구현 → 문서 업데이트”
- “PR 리뷰 → 위험 포인트 체크 → 성능 검토 → 코멘트 작성”

#### 왜 명령어와 다른가?

- **명령어(command)** 가 “실행 트리거”에 가깝다면
- **스킬(skill)** 은 “실행 절차 묶음”에 가깝습니다.

즉,
명령어는 버튼,
스킬은 그 버튼을 눌렀을 때 수행되는 플레이북이라고 보면 됩니다.

---

### 5-4. Command(커맨드)

원문에서는 commands를 `/plan`, `/tdd`, `/code-review` 같은 **레거시 슬래시 엔트리**라고 설명합니다. citeturn465257view0turn685678view1

쉽게 말하면:

- 사용자가 빠르게 호출하는 단축 명령
- 자주 쓰는 작업을 표준화하는 진입점

예:

- `/plan` → 계획 모드 시작
- `/tdd` → 테스트 우선 개발 워크플로우 시작
- `/evolve` → 학습된 패턴을 스킬로 승격

즉,
**command는 사용자 인터페이스**, **skill은 내부 작업 절차**에 더 가깝습니다.

---

### 5-5. Hook(훅)

훅은 어떤 이벤트 전후에 **자동으로 실행되는 연결 지점**입니다.

원문은 `PreToolUse`, `PostToolUse`, `SessionStart`, `Stop`, `PreCompact` 같은 훅 타입을 설명하며, ECC의 hooks.json이 7개 이벤트 타입을 활용한다고 적고 있습니다. citeturn685678view0

쉽게 비유하면:

- 문 열기 전에 손 소독하기
- 커밋 후 자동 포맷팅하기
- 테스트 실행 후 결과 저장하기

같은 **자동화 체크포인트**입니다.

#### 예시

- 도구 실행 전: 위험 명령인지 검사
- 도구 실행 후: 로그 저장
- 세션 시작 시: 프로젝트 규칙 로드
- 컨텍스트 압축 전: 중요한 메모 백업

#### 왜 중요하냐?

AI가 똑똑해도,
매번 사람이 “이제 이거 검사해”, “끝났으면 로그 남겨”라고 말하면 비효율적입니다.
그래서 훅은 **사람이 반복해서 말해야 하는 습관을 자동화**합니다.

---

### 5-6. Rule(룰)

룰은 프로젝트에서 지켜야 할 **행동 규칙**입니다.

원문은 `.claude/rules/` 아래에 보안, 코딩 스타일, 테스팅, Git 워크플로우 같은 규칙 파일이 모듈별로 구성된다고 설명합니다. citeturn685678view0

예:

- TypeScript에서는 any를 최소화
- Python에서는 pytest 기준으로 테스트 작성
- 보안 관련 파일은 직접 수정 전에 리뷰 필수
- PR 전엔 lint/test 필수

#### 왜 필요한가?

AI는 한 세션에서는 잘 따라도,
다음 세션에서는 규칙을 잊거나 다른 스타일로 답할 수 있습니다.

룰을 따로 두면:

- 일관성 유지
- 팀 규칙 반영
- 프로젝트 품질 기준 강제

가 쉬워집니다.

---

### 5-7. Frontmatter

원문 예시에서 `---` 로 감싼 YAML 영역이 나옵니다. 이것이 **frontmatter** 입니다. citeturn685678view1

예:

```yaml
---
name: planner
description: Expert planning specialist for complex features
tools: ["Read", "Grep", "Glob"]
model: opus
---
```

이건 문서 앞부분에 붙는 **메타데이터 블록**입니다.

쉽게 말하면:

- 이 파일 이름이 뭔지
- 무슨 역할인지
- 어떤 도구를 쓸 수 있는지
- 어떤 모델을 선호하는지

를 기계가 읽기 좋은 방식으로 적는 것입니다.

즉,
본문은 “어떻게 행동할지”이고,
frontmatter는 “이 에이전트가 어떤 존재인지”를 설명합니다.

---

### 5-8. MCP

원문은 MCP를 **외부 서비스 연결** 문맥에서 언급하면서,
너무 많이 연결하면 컨텍스트 윈도우가 잠식될 수 있다고 경고합니다. 제작자 경고로 “200K 컨텍스트가 실제로는 훨씬 줄 수 있다”는 취지의 설명도 나옵니다. citeturn685678view0

초보 관점에서는 이렇게 이해하면 됩니다.

- AI가 로컬 파일만 보는 것이 아니라
- 외부 도구, 서버, 서비스와 연결되도록 해 주는 인터페이스

예:

- GitHub 읽기
- 문서 서버 조회
- 데이터베이스 확인
- 브라우저/테스트 도구 연결

#### 왜 주의해야 하나?

연결이 많아질수록 편해지지만,
동시에 다음 문제가 생깁니다.

- 도구 설명이 길어짐
- 모델이 이해해야 할 범위 증가
- 토큰 낭비
- 보안 표면 확대

그래서 이 글은 MCP를 “많을수록 좋다”가 아니라,
**필요한 만큼만 활성화하라**는 관점으로 설명합니다. citeturn685678view0

---

### 5-9. Context Window(컨텍스트 윈도우)

이건 AI가 한 번에 참고할 수 있는 텍스트 범위입니다.

쉽게 말하면 **작업 기억 공간**입니다.

- 프롬프트
- 코드 일부
- 규칙
- 도구 설명
- 이전 대화

가 다 여기에 들어갑니다.

원문이 MCP를 많이 켜면 실제 활용 가능한 컨텍스트가 줄 수 있다고 강조하는 이유도,
이 작업 기억 공간이 무한하지 않기 때문입니다. citeturn685678view0

---

### 5-10. Token Optimization(토큰 최적화)

이건 AI에게 들어가는 텍스트 비용을 줄이면서,
필요한 정보는 유지하는 전략입니다.

쉽게 말하면:

- 길게 말해야 할 것을 짧게 정리하고
- 필요 없는 컨텍스트를 줄이고
- 반복되는 절차는 구조화해서 재사용하는 것

ECC가 에이전트/스킬/훅/룰을 나누는 이유도 결국
**토큰을 더 효율적으로 쓰기 위해서**라고 볼 수 있습니다.

---

### 5-11. Continuous Learning / Instinct

원문에서 가장 흥미로운 개념 중 하나입니다.

글에 따르면 ECC는 도구 사용 패턴을 훅으로 관찰하고,
이를 신뢰도 점수와 도메인 태그를 가진 **Instinct** 로 저장합니다. 그리고 `/evolve` 명령어로 이런 패턴을 새로운 스킬/커맨드/에이전트로 발전시킬 수 있다고 설명합니다. 프로젝트별 스코프를 두어 서로 오염되지 않게 한다는 점도 강조합니다. citeturn685678view2

쉽게 말하면:

1. AI가 자주 하는 좋은 작업 패턴을 관찰한다.
2. 그 패턴을 기억한다.
3. 나중에는 그걸 재사용 가능한 공식 절차로 바꾼다.

즉,
**즉흥적인 잘한 행동을, 재사용 가능한 시스템으로 승격**하는 개념입니다.

이걸 “학습”이라고 부르지만,
모델 자체를 재훈련하는 게 아니라
**작업 패턴을 운영 레벨에서 축적하는 것**에 가깝습니다.

### 5-12. AgentShield

원문은 AgentShield를 ECC와 연결된 독립 npm 패키지로 소개하며,
시크릿 탐지, 권한 감사, 훅 인젝션 분석, MCP 위험 분석, 설정 검토 등 5개 카테고리 스캔을 제공한다고 설명합니다. 또한 `--opus` 옵션을 통한 심층 분석, CI 통합, 다양한 출력 형식도 언급합니다. citeturn535231view2turn685678view2

쉽게 말하면 AgentShield는:

> **“AI 에이전트 설정이 위험하지 않은지 검사하는 보안 점검기”**

입니다.

왜 필요하냐면,
AI 에이전트는 단순 텍스트 생성기가 아니라
도구를 호출하고 파일을 읽고 명령을 실행할 수 있기 때문입니다.

그래서 위험 포인트도 생깁니다.

- 비밀 키 노출
- 위험한 도구 권한
- 악성 훅 삽입
- 외부 MCP 연결 취약점

즉,
예전에는 “앱 코드 보안”만 보면 됐다면,
이제는 **에이전트 운영 설정 자체의 보안**도 봐야 합니다.

## 7. 초보자가 특히 헷갈릴 포인트 정리

### Q1. 이건 결국 프롬프트 엔지니어링이랑 같은가?

완전히 같지는 않습니다.

- **프롬프트 엔지니어링**: 말을 어떻게 하느냐
- **하네스 엔지니어링**: 일을 시키는 환경 전체를 어떻게 설계하느냐

즉 프롬프트가 “대화 문장”이라면,
하네스는 “운영 시스템”에 가깝습니다.

---

### Q2. 에이전트가 많을수록 좋은가?

아닙니다.
원문도 필요한 것만 선택 도입하라고 권합니다. citeturn685678view3turn535231view7

에이전트가 너무 많으면:

- 관리가 어렵고
- 어떤 걸 써야 할지 헷갈리고
- 컨텍스트/권한/설정이 오히려 복잡해집니다.

작게 시작해서 필요한 만큼 늘리는 게 맞습니다.

---

### Q3. Instinct는 진짜 AI가 스스로 학습한다는 뜻인가?

엄밀히 말하면 “모델 재학습”은 아닙니다.
원문 설명상 **작업 패턴을 관찰해 구조화된 운영 자산으로 저장/승격**하는 방식에 가깝습니다. citeturn685678view2

즉,
가중치를 바꾸는 머신러닝 학습이라기보다
**좋은 습관을 작업 시스템으로 굳히는 것**입니다.

---

### Q4. 보안 가이드가 왜 이렇게 강조되는가?

AI 코딩 에이전트는 파일을 읽고, 명령을 실행하고, 외부 도구를 사용할 수 있기 때문입니다.
원문은 “악성 텍스트가 컨텍스트에 들어올 것을 전제하라”는 제작자의 보안 철학까지 인용합니다. citeturn685678view1

즉,
문제가 생기면 단순 오답 수준이 아니라
**권한 오남용** 으로 이어질 수 있습니다.

그래서 보안은 선택이 아니라 운영 기본값이 됩니다.

---

### Q5. 이 글을 읽고 내가 당장 따라 해야 하나?

무조건은 아닙니다.
원문도 선택 도입을 권하고, 커뮤니티 비판 항목도 함께 언급합니다. citeturn685678view3turn685678view4

- 중간 규모 프로젝트: 역할 분리와 훅 자동화가 유용

## 8. 이 글에서 진짜 배워야 할 핵심 메시지

원문은 ECC를 소개하지만,
사실 더 중요한 메시지는 따로 있습니다.

### 핵심 메시지 1: AI를 잘 쓰는 시대에서, 이제는 “운영을 잘 설계하는 시대”로 가고 있다

예전에는 이렇게 생각했습니다.

- 좋은 모델이면 끝
- 좋은 프롬프트면 충분

하지만 이 글은 그보다 한 단계 앞의 이야기를 합니다.

- 역할 분리
- 규칙 관리
- 도구 권한 통제
- 자동화 훅
- 보안 점검
- 패턴 재사용

즉 **AI 사용도 점점 소프트웨어 운영처럼 체계화되고 있다**는 메시지입니다.

### 핵심 메시지 2: 혼자 개발해도 팀의 방식으로 일할 수 있다

원문 제목에도 이 감각이 드러납니다.
“혼자서 팀처럼 개발하는 에이전트 셋업”이라는 표현은,
AI를 여러 역할로 분리해 **기획자/리뷰어/보안 담당/테스터처럼 운용**할 수 있다는 뜻입니다. citeturn465257view0turn685678view1

### 핵심 메시지 3: 강력한 구조는 동시에 과할 수도 있다

원문은 커뮤니티 비판도 함께 소개합니다. 즉 이 구조는 멋져 보이지만,
모든 프로젝트에 다 맞는 정답은 아닙니다. citeturn535231view6turn685678view4

그래서 중요한 건 “ECC를 그대로 쓰는가”가 아니라,
**내 프로젝트에 맞는 하네스 수준은 어디까지인가**를 판단하는 것입니다.

## 9. 당신 같은 학습자 관점에서 어떻게 받아들이면 좋은가

당신처럼 지금 AI 코딩, 하네스 엔지니어링, 자동화 구조를 배우는 입장이라면,
이 글을 이렇게 받아들이는 것이 좋습니다.

### 1단계
먼저 용어만 익히기

- agent
- skill
- command
- hook
- rule
- MCP
- context window
- instinct

이 정도만 구분해도 글이 훨씬 읽힙니다.

### 2단계
내 프로젝트에 대응시켜 보기

예를 들어 SQL 처리기나 Virtual DOM 프로젝트라면:

- planner 에이전트: 구현 단계 나누기
- code-reviewer: 구조 리뷰
- tdd-guide: 테스트 추가
- hooks: 포맷/빌드 체크 자동화
- rules: 코딩 스타일, 테스트 룰

처럼 연결해 볼 수 있습니다.

### 3단계
전체를 복사하지 말고 작은 하네스부터 시작하기

예:

- 규칙 파일 1개
- 자주 쓰는 작업 스킬 2개
- 안전 관련 훅 1개

이 정도만 있어도 이미 “하네스 엔지니어링”의 시작입니다.

## 10. 아주 짧은 최종 요약

이 글은 **Everything Claude Code(ECC)** 라는 프로젝트를 소개하면서,
AI 코딩 도구를 그냥 쓰는 수준을 넘어
**역할 분리 + 작업 절차 + 자동화 + 규칙 + 보안**으로 운영하는 방법을 설명하는 글입니다. citeturn465257view0turn535231view7

처음 보면 용어가 많은 이유는,
이 글이 단순 기능 설명이 아니라
**AI를 팀처럼 굴리는 운영 체계**를 다루고 있기 때문입니다.

가장 중요한 개념은 이것입니다.

> 하네스 엔지니어링은 “AI에게 좋은 질문을 하는 법”을 넘어서,
> **AI가 좋은 방식으로 일하게 만드는 시스템을 설계하는 일**이다.

# 가상 메모리의 연속성
- 프로세스는 "연속된 가상 주소 공간"을 갖지만, 실제 물리 메모리는 페이지 단위(4kB)로 흩어져 저장될 수 있다.
- 그 매핑 정보를 따라가는 시작점 : PML4
- x86-64

## 프로세스 입장에서는 연속된 가상 메모리 + 실제 물리 메모리 찾는 흐름
- 예를 들어 어떤 프로세스가 아래 주소를 사용한다고 해보자.

1. 프로세스 입장에서는 연속된 가상 메모리
```
가상 주소 공간

0x400000 ~ 0x403000
총 3 페이지 (4KB * 3 = 12KB)

프로세스 입장에선 연속적
[ page A ][ page B ][ page C ]
```

2. 실제 물리 메모리를 흩어져 있음
- 하지만 운영체제는 실제 RAM에서 빈 공간을 아무 데나 할당 가능
```
물리 메모리

0x1000 frame  -> page A
0xA000 frame  -> page B
0x5000 frame  -> page C

[ A ]      [ C ]         [ B ]
0x1000     0x5000        0xA000
```

3. 이걸 누가 기억하나?
- Page Table (in x86-64)
```
PML4
 └─ PDPT
     └─ PD
         └─ PT
             └─ Physical Frame
```

4. 예시
```
CPU가 0x401234에 접근한다고 가정
0000 0000 0/000 0000 00/00 0000 010/0 0000 0001/ 0010 0011 0100(2)

(1) 가상 주소 분해
x86-64 4KB paging
| PML4 | PDPT | PD | PT | OFFSET |
  9bit   9bit  9bit 9bit  12bit

PML4 index = 0
PDPT index = 0
PD index   = 2
PT index   = 1
offset     = 0x234
```

```
CPU는 현재 프로세스의 CR3 레지스터를 봄
CR3 -> 현재 프로세스의 PML4 물리 주소
ex. CR3 = 0x9000 -> 즉, 물리주소 0x9000에 PML4 존재
1001 0000 0000 0000

PML4[0] -> 0x9000 (1001 0000 0000 0000(2)) + (0 * 8byte)  PDPT 물리주소 = &(0x9000) -> 읽어보니 0x3000
PDPT[0] -> PD 물리주소 &(0x3000) -> 읽어보니 0x7000
PD[2] -> PT 물리주소 0x7000 + (2 * 8byte) = &(0x7010) -> 읽어보니 0x2000
PT[1] -> PD 물리주소 0x2000 + (1 * 8byte) = &(0x2008) -> 읽어보니 0xA000

-> 실제 물리 메모리가 0xA000에 존재
offset(0x234) -> 0xA000 + 0x234 = 0xA234
```

## 왜 굳이 가상 메모리를 만들고, 실제 물리 메모리를 흩어지게 저장하는가?
```
1. 연속된 큰 메모리를 실제 RAM에서 그대로 확보하기가 어렵기 때문
    - 운영체제가 훨씬 유연하게 메모리를 관리하기 위해

    - 중요한 이유
        - 1. 외부 단편화 해결 (옛날 contiguous allocation 방식)
            - 연속 공간이 없으면 실패
            - 하지만 paging은 페이지 단위로 아무 데나 배치 가능
        - 2. 프로세스 격리 가능
            - 각 프로세스는 자기만의 PML4를 가짐
            - 서로 메모리 침범 불가
            - 보안성 증가
            - 안정성 증가
        - 3. swap 가능
            - 운영체제는 심지어 "지금 안쓰는 페이지는 디스크로 빼버리자" 가능 (Paging Out)
            - RAM 부족 이어도 더 큰 메모리처럼 동작 가능
        - 4. 공유 메모리 가능
            - libc.so 같은 라이브러리
            - 모든 프로세스가 같은 물리페이지 공유 가능
                - Process A VA -> same PA
                - Process B VA -> same PA
        - 5. fork최적화 가능
            - fork 시 메모리 전체 복사
            - 그래서 부모와 자식이 같은 pa 공유하고, 쓰기 발생 시에만 복사
            - 운영체제는 "프로세스에게는 연속 메모리처럼 보이게 하고, 실제 RAM은 효율적으로 조각내서 사용"하기 위해 paging을 사용
    - 페이징 단위인 이유 (왜 4kB?)
        - 메모리 낭비 심함
        - 페이지 테이블이 너무 커짐
        - 그래서 적당한 타협점으로 4kB를 기본 페이지로 사용
    - 2,3,4,5는 가상메모리 없어도 구현 가능하지 않나?
        - "이론적으로는" 가상메모리 없이도 일부 구현 가능
        - 문제
            - 가상메모리가 없으면 너무 비효율적, 너무 복잡, 너무 제한적
        - 결론 : 가상 메모리 구조 덕분에 매우 자연스럽고 효율적으로 가능해진 것
```

## Swap에 대해
```
RAM 부족으로
프로세스 A의 어떤 페이지가 10분째 접근 안됨

1단계
physical page 내용을 디스크(swap area)에 저장

2단계
페이지 테이블 수정
VA -> Physical 0xA000
였는데, 이제 "현재 RAM에 없음" 이라고 표시 (Present bit = 0)

3단계
Physical frame 회수
0xA000
RAM 재사용 가능

-- 이때! 프로세스가 다시 접근 --
Page Fault (CPU 예외 발생)

OS가 처리
운영체제가
디스크에서 해당 페이지를 다시 읽음
            ↓
새 physical frame 할당
            ↓
페이지 테이블 다시 연결
            ↓
프로세스 재실행

프로세스 입장에선 아무것도 모름
-> 메모리 접근했는데 조금 느렸네? 정도로 보임

-- 그래서! "메모리가 부족해도 프로그램이 실행되는 이유" --
예를 들어 RAM = 8GB
실행중인 프로세스 총합 = 20GB

운영체제가 자주 쓰는 페이지만 RAM 유지하고 나머지는 디스크로 빼버림

RAM : ns 단위
SSD : ㎲ ~ ms 단위
그래서 page fault 많이 발생하면 Thrashing 발생 (운영체제가 계속 page in, page out 만 반복)

CPU는 거의 일 못함, 디스크 I/O만 엄청남
```

## 꼬리 질문

1. page in/out 할 때, 물리프레임만 지우나? 가상 주소까지도 함께 지우는지 궁금
```
보통 page out 시 물리 프레임과 page table 매핑만 끊고, 가상 주소 정보는 유지
흐름
[page out / eviction]
가상 주소 VA
        ↓
struct page는 SPT에 남아 있음
        ↓
기존 PML4 매핑은 제거됨
        ↓
물리 frame은 비워짐
        ↓
내용은 swap 또는 file system에 저장됨

즉, 지워지는 건 VA -> 물리 frame 매핑 정보
남는 건 VA에 대한 struct page 정보

[pintos 내에서도 eviction은 "프레임에서 페이지를 제거하고, 필요하면 swap table이나 file system에 쓰는 것"이라고 설명하고, page table reference를 제거한다고 되어 있음. 또한 SPT는 page fault 때 "해당 데이터가 어디에 있는지" 찾는 용도]
```

2. 만약 저장해놓는다면 그것의 장점은?
```
저장해놔야 나중에 다시 접근했을 때 복구가 가능

어떤 유저 프로그램이 0x8049000 주소를 쓰다 page out 발생되었다고 가정
0x8049000 접근
-> 현재 page table에 매핑 없음
-> page fault 발생
-> SPT에서 0x8049000 검색
-> 이 페이지는 swap slot 3에 있는 것을 확인
-> frame 새로 할당 (여기부터의 과정이 궁금, 실제로 빈 공간을 찾아서 매핑을 찾는 과정이 어떻게 되지?) + (한페이지씩 비트맵을 통해 찾아서 할당하는가?, 페이징을 관리하는 버디시스템 처럼 공간을 나눠져 있는데 그것을 찾는것인가?, 또한 실제 OS는 어떻게 이뤄져 있는가?)
-> swap에서 읽어옴
-> 다시 VA -> frame 매핑

-- 만약 가상 주소 정보까지 지워버리게 될 경우
page fault가 났을 때, 커널 입장에서는 이게 유효한 접근인지? 스택 증가인지? swap에서 가져와야 하는지? 파일에서 다시 읽어야 하는지 판단할 수 없음
```
```
SPT에는 보통 아래와 같은 정보가 남아 있어야 하고
SPT는 각 page에 대해 frame/disk/swap 위치, active/inactive 같은 추가 정보를 추적하는 "per-process" 자료구조라고 설명

struct page {
    void *va;              // 유저 가상 주소
    struct frame *frame;   // 현재 물리 프레임, 없으면 NULL
    enum vm_type type;     // anon/file/uninit 등
    bool writable;
    // swap 위치 또는 file 위치 정보
};
```

3. swap in/out이 발생하는 조건이 뭔지 궁금
```
-- 기본적으론 --
swap out
물리 프레임 비우고
PML4 매핑 정보 지우고
SPT의 struct page는 유지한 후
내용은 swap/file에 저장
-> swap disk에는 "페이지 내용(4KB 데이터)" 자체가 저장
-> 즉, 주소 정보만 저장되는게 아니라 실제 프레임 안에 있던 데이터 전체가 저장

swap in
page fault 발생
SPT 조회
swap/file에서 다시 읽고
PML4 매핑 복구

-- 가상 주소 정보를 저장하고 있으면, 결국 프로세스 메모리가 끝없이 커지는 것 아닌가? --
가상 주소 공간(VA Space)는 '주소 범위'일 뿐이고,
실제 메모리 사용량은 '현재 물리 프레임 + 메타데이터(SPT 등)'에 의해 결정

즉, 주소 정보는 8byte
SPT 정보 또한 수십 바이트 수준

-- VM의 핵심 아이디어 --
"실제 데이터는 필요할 때만 RAM에 올리고, 나머지는 아주 작은 메타데이터만 유지"라는 철학

"예를 들어 어떤 프로세스가 1GB virtual memory를 가진다고 가정 -> 하지만 실제로 지금 사용하는 건 12MB뿐일 수도 있음"

OS는 1GB 전체를 RAM에 올리지 않고, SPT: "이 가상 주소는 어디에 있음" 정도만 관리
진짜 메모리 사용량 : 가상 주소 개수가 아닌 현재 RAM에 올라와 있는 frame 수
```

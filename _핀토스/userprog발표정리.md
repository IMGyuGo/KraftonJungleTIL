# Case Emerge

1. 논의된 내용
```
fd_table을 구현 중 저희 팀은 이런 상황을 고민하게 되었습니다.

open -> fd 3
open -> fd 4
close(3)
open -> fd 5
close(4)
open -> fd 6

닫힌 fd를 재사용하지 않으면
fd 번호가 계속 증가하는 fd leak 문제가 발생할 수 있었습니다.

그렇다면
1. fd를 어떻게 재사용할 것인가?
2. Array와 List 중 어떤 구조가 적절할까?
```

# Opinion

```
배열 방식을 사용하면
배열을 순회하며 NULL 슬롯을 발견하면 재사용 하는 방식이 좋다고 판단하였고
장점
- 구현 직관적
- fd 접근 O(1)

단점
- 빈 슬롯 탐색 시 O(N)


```

1. 1에 대한 의견
```
배열로 사용해 for문을 반복해서 돌려 NULL인 부분을 찾아 다시 할당한다.

장점 : 재사용 가능
단점 : O(1) -> O(N)이 됨
```

```
list는 주소로 접근하기 때문에 free로 메모리 해제한 부분의 fd를 찾는 로직
즉 find_fd()를 만들어
2 3 x 5 6 (먼저 전체 탐색을 돌려 x를 찾고)
    ↓
2 3 5 6 4 (다음 open 시 제일 뒤에 다시 넣어주는 방법)

이것 또한 O(N)이긴 하지만, 실제로 fd가 배정된 목록만 탐색하므로 배열보단 빠르다.
```

2. 2에 대한 의견
```
직관적이고 일반적인 배열을 사용하는게 좋을 것 같다.
리스트를 쓴다고 큰 메리트가 있지는 않고, 나중에 다른 시스템 콜 구현할 때 코드 구현이 많이 달라질 수 있을 것 같다.
```

# Problem Solving
1. 1에 대한 해결 과정
```
처음에는 fdt에 파일을 저장하거나 새로 만든 file_entry를 저장하기 때문에
파일의 크기가 fdt의 할당하는 공간에 영향을 끼칠 줄 알고 리스트를 사용해야 한다고 생각하긴 했었다.
탐구결과
fd_table[3] ──> struct file
                 └─ inode *
                      └─ sector 번호
파일 구조체 안에 메타데이터 (1. 디스크 위치를 알 수 있는 디스크 섹터 번호, 2. 열린 횟수, 3. 삭제 여부, 쓰기 가능 여부, 4. 파일 크기 등등)만 포함된 정보라
실제 fdt안에 들어가 있는 파일의 크기는 다 동일하다는 결론을 얻고
고려해야 할 정보는 단지 비어 있는 fd 번호가 있는지만 체크해보면 되는 것을 깨달았다.
```

2. 2에 대한 해결 과정
```
이런 논의가 발전하면서 실제 리눅스의 fdt의 관리를 어떻게 하냐? 라는 질문의 꼬리로 이어졌습니다.

일단 fdt는 각각의 프로세스마다 독립적으로 FD 테이블을 유지(PCB 내에 존재)
파일 오픈 시 가장 작은 정수 번호(0부터 시작)해서 (0: stdin, 1: stdout, 2: stderr)

실제 Linux 커널은 Pintos 처럼 단순 배열 하나만 두고 관리하지 않고,
프로세스마다 files_struct -> fdtable 구조를 두고, 그 안에서
- fd 슬롯 배열
- 사용 중 여부 bitmap
- close-on-exec bitmap
- 동적 확장 로직
- reference counting
- RCU synchronization
등을 함께 사용한다.

task_struct
 └── files_struct
      └── fdtable
           ├── struct file *fd[]        // 실제 파일 객체 배열
           ├── open_fds bitmap          // 사용 중인 fd
           ├── close_on_exec bitmap     // exec 시 닫을 fd
           └── max_fds

리눅스도 결국 "배열 기반"
1. 배열을 쓰는 이유 : fd lookup이 엄청 자주 발생
    - read(fd, ...)
    - write(fd, ...)
    - close(fd)
    - dup2(fd)
모든 syscall이 fd -> struct file* 변환
그래서 리눅스는 file = current->files->fdt->fd[fd]; 처럼 O(1) 접근

2. 만약 close를 안 해서 fd가 계속 증가
    - RLIMIT_NOFILE
로 관리
RLIMIT_NOFILE : 프로세스별 최대 fd 제한 (보통 1024) -> 즉, 1024개가 넘으면 EMFILE 에러 발생

3. fd 재사용 방식
Linux는 bitmap에서 가장 먼저 비어있는 0 bit 탐색
fd:
0 1 2 3 4 5 6 7

bitmap:
[1] [1] [1] [0] [1] [0] [0] [0]
```

# Conclusion
```
fd는 랜덤 접근이 중요
read(57)을 하면 57 번째 fd 즉시 접근이 필요

list면 O(n) 탐색 필요 -> 매우 비 효율적

Linux가 bitmap을 쓰는 이유
00101111 -> CPU bit instruction 사용 가능
fd 1024개여도 1024bits = 128 bytes 뿐
```

# 발표 대본

```
1
실제 FDT 구현 중 있었던 이슈를 중심으로 발표하겠습니다.

2
팀 회의 중 한 가지 고민이 생겼습니다.
fd를 단순히 증가시키는 방식으로 구현하면,
open을 두번해서 3,4를 할당하고 3을 닫고 다시 open을 하면 close된 fd를 재사용하지 못하고
fd 값이 계속 증가하는 문제가 발생했습니다.

그래서 저희는 fd를 어떻게 재사용할 것인가?
Array와 List 중 어떤 구조가 적절할까? 를 중심으로 토의하게 되었습니다.

3
배열 방식은
구현이 직관적이고 fd 번호로 바로 접근 가능하기 때문에 빠르지만,
빈 슬롯을 다시 찾는데 걸리는 시간이 길다는 단점이 있었습니다.

반면 리스트 방식은
실제 사용 중인 fd만 관리하므로 빈 슬롯 탐색 측면에선 효율적일 수 있지만,
read(57)같은 특정 fd 접근 시 리스트를 순회해야 하므로 랜덤 접근에 불리하다는 단점이 있었습니다.

그래서 fd는 번호 기반 랜덤 접근이 핵심이라는 결론을 내렸고, 리스트보다 배열 구조가 적합하다 판단했습니다.

4
그 과정에서 또 다른 의문이 생겼습니다.
fdt안에 file 객체 자체를 저장하면, 파일 크기에 따라 공간도 계속 달라지는 것 아닐까?

처음엔 배열 보다 리스트가 더 적합하지 않을까 생각했습니다.
하지만 구조를 조사해보니 실제 FDT에는 파일 데이터 자체가 아니라 포인터만 저장된다는 점을 확인할 수 있었고
fdt는 고정 크기의 포인터만 관리하므로 파일 크기 자체는 크게 영향을 주지 않는다는 사실을 알게 되었습니다.
그리고 이 논의는 자연스럽게 실제 linux는 fdt를 어떻게 관리할까? 라는 질문으로 이어졌습니다.

5
조사 결과 실제 linux 역시 배열 기반 fdt를 사용하고 있었고
fd가 결국 read,wrie,close처럼 접근이 매우 중요하기 때문이라는 점도 알게 되었습니다.

그리고 fd 재사용 문제는 BITMAP을 통해 해결하고 있었습니다.
0,1로 관리하여 빈 fd를 찾아 재사용하는 방식입니다.
처음엔 비트맵도 배열이므로 탐색 비용이 클 것이라 생각했지만, 실제 OS는 word 단위로 탐색하므로
64bit 환경에선 한 번에 64개의 fd 상태를 검사할 수 있다는 점도 알게 되었습니다.

6
정리하면,
fd는 랜덤 접근이 중요하므로 배열 기반 구조가 적합했고,
fd 재사용 문제는 BITMAP을 통해 효율적으로 해결 가능하며
실제 Linux 역시 배열 + BITMAP 기반으로 FDT를 관리하고 있음을 확인할 수 있었습니다.

여기까지 마치고 다음으로 넘기도록 하겠습니다.
```

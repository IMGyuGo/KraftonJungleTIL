# 0515 개념 코어타임 정리

## 1. 전체 흐름 — Page Fault가 왜 발생하는가

CPU가 어떤 가상 주소(Virtual Address)에 접근하면:

```text
VA 접근
→ PML4 → PDPT → PD → PT 탐색
→ 페이지 없음 / 권한 문제 발생
→ Page Fault 발생 (#PF)
```

이후 흐름:

```text
page_fault()
→ vm_try_handle_fault()
→ SPT에서 페이지 탐색
→ 복구 가능 여부 판단
→ 가능하면 frame/page 생성
→ 불가능하면 process 종료
```



---

# 2. page_fault()에서 핵심인 것

## (1) struct intr_frame *f

페이지 폴트 발생 당시 CPU 상태를 담고 있는 구조체.

포함 정보:

* RIP: fault 발생 instruction 주소
* RSP: stack pointer
* error_code
* user/kernel mode 여부

즉:

```text
"CPU가 어떤 상태에서 죽었는가?"
```

를 담고 있음.



---

## (2) 가장 중요한 값: error_code

페이지 폴트 원인을 비트 단위로 저장함.

핵심 비트:

| 매크로 | 의미           |
| --- | ------------ |
| PFP | Present bit  |
| PFW | Write 여부     |
| PFU | User mode 여부 |

정의:

```c
#define PF_P 0x1
#define PF_W 0x2
#define PF_U 0x4
```



---

# 3. 비트마스크 해석 방식

예시:

```text
error_code = 0x6
```

2진수:

```text
0110
```

## PFP 검사

```c
error_code & PF_P
```

```text
0110
0001
----
0000
```

→ 0

즉:

```text
present == false
→ 페이지가 현재 메모리에 없음
```

---

## PFW 검사

```text
0110
0010
----
0010
```

→ true

즉:

```text
write 접근이었다
```

---

## PFU 검사

```text
0110
0100
----
0100
```

→ true

즉:

```text
user mode에서 발생
```

# 4. CR2 레지스터의 역할

핵심:

```text
CPU는 Page Fault 발생 시
문제가 된 가상 주소(VA)를
CR2 레지스터에 저장한다.
```

읽어오는 코드:

```c
fault_addr = rcr2();
```

즉:

```text
rcr2()
= read CR2
```



---

# 5. 왜 interrupt를 잠깐 끄는가?

이유:

```text
CR2는 "가장 최근 page fault 주소"를 저장함.
```

그런데 interrupt 중 다른 page fault가 발생하면:

```text
CR2 값이 덮어씌워질 수 있음
```

그래서:

```c
intr_disable()
fault_addr = rcr2()
intr_enable()
```

형태로 안전하게 읽음.



---

# 6. vm_try_handle_fault()의 역할

실질적인 Page Fault 처리기.

여기서 하는 것:

* fault 원인 분석
* 주소 유효성 검사
* user/kernel 검사
* stack growth 가능 여부 판단
* lazy loading 여부 판단
* SPT에서 page 찾기
* frame claim

즉:

```text
"이 fault를 살릴 수 있는가?"
```

를 판단하는 메인 함수.



---

# 7. SPT 흐름

현재 thread의 SPT에서 페이지 탐색:

```c
spt_find_page()
```

흐름:

```text
thread_current()
→ current->spt
→ hash table 탐색
```

페이지가 없으면:

```text
stack growth 가능한지 확인
```

가능하면:

```text
vm_stack_growth()
```

호출.



---

# 8. claim의 의미

```text
claim
= 실제 frame 확보 + page 연결
```

즉:

```text
가상 페이지를 실제 물리 메모리에 올리는 과정
```

관련 함수:

* vm_claim_page
* vm_do_claim_page



---

# 9. Hash Insert 내부 흐름

SPT 내부는 hash table 기반.

```c
hash_insert()
```

흐름:

```text
1. bucket 찾기
2. 같은 원소 존재 여부 확인
3. 없으면 삽입
4. 있으면 삽입 안함
```

핵심:

```text
"같은 page가 이미 존재하는지 검사"
```

# 10. Exception → Page Fault 연결 흐름

## 전체 연결 구조

```text
main()
→ exception_init()
→ IDT 등록
→ vector 14 = page_fault
```

CPU가 page fault 발생시키면:

```text
interrupt handler
→ vector 번호 확인
→ 14번이면 page_fault 호출
```

즉:

```text
#PF = interrupt vector 14
```

# 11. 내부 인터럽트 vs 외부 인터럽트

## 외부 인터럽트

예:

* timer interrupt
* keyboard interrupt

특징:

```text
다음 instruction부터 재개
```

---

## 내부 인터럽트(Exception/Fault)

예:

* divide by zero
* page fault

특징:

```text
현재 instruction 자체 문제
```

# 12. Load / Store / Instruction Fetch 의미

## Load

메모리 읽기

```c
x = arr[0];
```

---

## Store

메모리 쓰기

```c
arr[1] = 4;
```

---

## Instruction Fetch

RIP 기준으로 명령어 자체 읽기.

즉:

```text
CPU가 instruction byte를 가져오는 행위
```

이 과정에서도 page fault 가능.



---

# 13. Zero Fill / BSS 의미

파일 크기보다 메모리 크기가 더 클 수 있음.

이유:

```text
BSS 영역
```

예:

```c
int a;
```

초기화 안 했지만 메모리에서는 0이어야 함.

그래서:

```text
파일에 없는 영역까지
메모리에서는 0으로 채워야 함.
```

이 과정을:

```text
zero fill
```

이라고 함.

# 14. 핵심 흐름 한 번에 정리

```text
유저 프로그램 실행
→ VA 접근
→ PT/PML4 탐색
→ page 없음 or 권한 문제
→ CPU가 #PF 발생
→ fault VA를 CR2 저장
→ vector 14 호출
→ page_fault()
→ error_code 분석
→ vm_try_handle_fault()
→ SPT 탐색
→ stack growth / lazy loading 판단
→ claim(frame 확보)
→ 복구 성공 or 종료
```

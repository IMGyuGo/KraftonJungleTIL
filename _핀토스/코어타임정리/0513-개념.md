이번 코어타임에서는 Pintos의 Supplemental Page Table(SPT) 구현을 위해 필요한 `hash table` 구조와 동작 원리를 중심으로 정리했어. 특히 `hash_init`, `hash_find`, `hash_insert`, `rehash`, `hash_entry` 같은 내부 구현 흐름을 실제 VM 흐름과 연결해서 이해하는 시간이었음. 

# 핵심 주제

* SPT에서 왜 Hash Table을 사용하는가
* `struct page` 와 `hash_elem` 관계
* VA(Virtual Address)를 기준으로 탐색하는 이유
* `hash_find`, `hash_insert` 내부 동작
* bucket index 계산 방식
* rehash가 필요한 이유
* Pintos hash API가 `equal` 대신 `less`를 사용하는 이유
* VM의 `spt_find_page`, `spt_insert_page` 흐름

---

# 1. SPT에서 Hash Table을 사용하는 이유

페이지 폴트는 매우 자주 발생할 수 있기 때문에,
가상 주소(VA)를 빠르게 찾아야 함.

그래서 Pintos는 SPT를 Hash Table 기반으로 구현함. 

구조는 대략 이런 느낌:

```c
struct page {
    void *va;
    struct hash_elem hash_elem;
};
```

즉:

```text
SPT(Hash Table)
    ↓
bucket[]
    ↓
linked list
    ↓
hash_elem
    ↓
struct page
```

---

# 2. 왜 VA만으로 찾을 수 있는가?

핵심 개념:

> "SPT는 VA를 기준으로 동작한다"

`page_hash()` 와 `page_less()` 모두 VA를 사용해서 비교함. 

그래서 실제로 `spt_find_page()` 구현 시:

```c
struct page p;
p.va = va;
hash_find(&spt->hash, &p.hash_elem);
```

처럼 "더미 페이지"를 만들어도 탐색 가능함. 

이유:

* hash 계산도 VA 기준
* less 비교도 VA 기준
* bucket 선택도 VA 기준

즉:

```text
VA만 알면
→ hash 계산 가능
→ bucket 찾기 가능
→ linked list 순회 가능
→ page 찾기 가능
```

---

# 3. hash_entry()의 의미

이 부분을 많이 깊게 파고들었음.

`hash_elem`만 가지고 실제 `struct page` 주소를 역산하는 매크로.

```c
hash_entry(e, struct page, hash_elem)
```

의미:

```text
hash_elem 주소
→ struct page 내부에서 offset 계산
→ 실제 struct page 시작 주소 복원
```

즉:

```text
page 구조체 안에
hash_elem이 포함되어 있기 때문에
offset 역산이 가능함
```



---

# 4. hash_bytes() / FNV Hash

해시값 생성 방식도 다룸.

```c
hash = (hash * FNV_64_PRIME) ^ byte;
```

핵심:

* 랜덤값 생성이 아님
* 동일 입력 → 동일 hash 보장
* 바이트 단위로 섞으면서 hash 생성

즉:

```text
VA 주소값
→ byte 단위 분해
→ 반복 XOR + PRIME 곱
→ 최종 hash 값 생성
```



---

# 5. Bucket Index 계산 방식

이 부분 핵심.

Pintos는 `%` 대신 bit 연산 사용:

```c
index = hash & (bucket_cnt - 1);
```

왜 가능할까?

bucket 개수를 항상 2의 제곱으로 유지하기 때문. 

예:

```text
bucket_cnt = 8
bucket_cnt - 1 = 7 = 0b111

hash & 0b111
→ 마지막 3bit만 남음
→ 0~7 index 생성 가능
```

즉:

```text
mod 연산 대신
bit masking으로 최적화
```

---

# 6. 왜 bucket count를 2의 제곱으로 유지하는가?

이유:

```text
hash & (bucket_cnt - 1)
```

이 최적화를 사용하기 위해서.

그래서 rehash 과정에서:

```c
is_power_of_2()
```

검사 수행. 

그리고:

```text
원소 수 증가
→ 충돌 증가
→ bucket 확장 필요
→ rehash 발생
→ 모든 원소 재배치
```

---

# 7. hash_insert 동작 흐름

핵심 흐름:

```text
1. hash_find로 기존 원소 존재 확인
2. 없으면 linked list에 insert
3. elem_cnt 증가
4. rehash 필요 여부 검사
```



특히:

```c
old == NULL
```

의미를 많이 이야기했음.

즉:

```text
같은 VA를 가진 page가 없음
→ 새로 삽입 가능
```

---

# 8. Pintos가 equal 대신 less를 사용하는 이유

재밌는 포인트였음.

Pintos hash API는:

```text
equal 함수 없음
```

대신:

```c
less(a, b)
```

만 사용함. 

그래서 equality 판단도:

```c
!less(a, b) && !less(b, a)
```

로 처리함.

즉:

```text
a < b 아님
b < a 아님
→ 둘은 같음
```

왜 이렇게 만들었는지는 명확하지 않았고,
결론은:

```text
"Pintos hash API 설계 자체가 그렇다"
```

정도로 정리됨.

# 9. supplemental_page_table_init()

실제 구현 흐름도 정리함.

```c
void
supplemental_page_table_init(struct supplemental_page_table *spt) {
    hash_init(&spt->hash, page_hash, page_less, NULL);
}
```

의미:

```text
각 thread/process마다
자신만의 SPT(Hash Table)를 가진다
```



즉:

```text
새 프로세스 생성
→ SPT 초기화
→ page 삽입/탐색 가능
```

# 10. VM 흐름과 연결

이제 VM에서는 기존 load_segment가 아니라:

```c
vm_alloc_page_with_initializer()
```

경로를 타게 됨. 

그리고 내부에서:

```text
spt_find_page()
spt_insert_page()
```

구현이 필요함.

즉 현재 단계는:

```text
SPT 기반 page 관리 시스템 구축 단계
```

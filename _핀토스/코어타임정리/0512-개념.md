# Pintos VM / SPT 스터디 내용 정리

업로드된 스터디 내용을 기반으로 핵심 흐름 위주로 정리했습니다. 

---

# 1. SPT(Supplemental Page Table)란?

SPT는:

> "가상 페이지 주소(VA)를 기반으로 페이지의 상태 정보를 관리하는 추가 페이지 테이블"

입니다.

기존 PML4(Page Table)는:

* 현재 RAM에 올라와 있는 페이지
* 즉 실제 물리 프레임과 연결된 페이지

만 관리합니다.

하지만 Virtual Memory에서는:

* 아직 RAM에는 없음
* 하지만 "유효한 페이지"

가 존재할 수 있습니다.

예시:

* Lazy Loading 된 코드 페이지
* mmap 페이지
* swap out 된 페이지
* stack growth 대상 페이지

이런 정보는 PML4만으로는 알 수 없기 때문에
SPT가 필요합니다. 

---

# 2. SPT는 무엇을 저장하나?

SPT는 보통:

```c
Key   : Page Virtual Address (페이지 시작 주소)
Value : struct page
```

형태로 저장합니다. 

즉:

| 역할    | 의미                         |
| ----- | -------------------------- |
| Key   | 페이지 시작 가상주소                |
| Value | 해당 페이지의 메타데이터(struct page) |

---

# 3. struct page란?

중요한 개념:

* "페이지(page)"
* "struct page"

는 다릅니다.

## 실제 페이지(page)

* 4KB 가상 메모리 단위

## struct page

* 그 페이지를 설명하는 메타데이터
* 운영체제가 관리용으로 사용하는 구조체

즉:

```text
가상 페이지
↓
운영체제가 설명용 메타데이터(struct page)로 관리
```

---

# 4. 왜 SPT를 Hash Table로 구현하는가?

핵심 이유:

> 페이지 폴트가 매우 자주 발생하기 때문

페이지 폴트 발생 시:

```text
fault address 발생
→ SPT 조회
→ 해당 페이지 찾기
```

를 매우 빠르게 해야 합니다.

만약 리스트라면:

```text
O(N)
```

으로 순회해야 합니다.

하지만 해시 테이블은:

```text
평균 O(1)
```

에 가까운 접근이 가능합니다. 

---

# 5. Pintos Hash Table 구조

Pintos hash 구조는:

```text
Hash Table
 ├── Bucket 배열
 │     ├── 연결리스트
 │     ├── 연결리스트
 │     └── 연결리스트
```

형태입니다. 

## 동작 방식

### 1) 해시 계산

```text
hash(va)
```

### 2) bucket index 계산

```c
index = hash % bucket_count
```

### 3) 해당 bucket 연결리스트 순회

같은 bucket 안에서만 비교 탐색 수행

---

# 6. 왜 Bucket을 쓰는가?

해시 충돌 때문입니다.

서로 다른 VA라도:

```text
hash 값이 동일
```

할 수 있습니다.

그래서:

```text
같은 bucket 안에 여러 요소 저장
```

을 위해 연결리스트를 사용합니다.

---

# 7. 왜 fault address를 page boundary로 내리는가?

핵심:

> SPT는 "페이지 시작 주소" 기준으로 저장되기 때문

예시:

```text
fault address = 0x401234
```

하지만 SPT에는:

```text
0x401000
```

이 저장되어 있습니다.

그래서:

```c
pg_round_down(fault_addr)
```

을 통해:

```text
0x401234 → 0x401000
```

으로 내려서 검색합니다. 

---

# 8. 왜 Round DOWN인가?

페이지는:

```text
[0x401000 ~ 0x401FFF]
```

처럼 시작 주소 기준으로 관리됩니다.

따라서:

```text
0x401234
```

는:

```text
0x401000 페이지 내부 주소
```

입니다.

만약 round up 하면:

```text
0x402000
```

이 되어:

전혀 다른 페이지를 가리키게 됩니다.

---

# 9. VM Type 정리

Pintos VM에서는 페이지 종류를 구분하기 위해 type을 둡니다. 

대표적으로:

| 타입            | 의미                     |
| ------------- | ---------------------- |
| VM_UNINIT     | 아직 초기화 안 된 페이지         |
| VM_ANON       | 스택/힙 같은 anonymous page |
| VM_FILE       | 파일 기반 페이지              |
| VM_PAGE_CACHE | 파일시스템 캐시               |

---

# 10. Lazy Loading이란?

핵심:

> 실제 접근 전까지 RAM에 안 올리는 것

예시:

```text
ELF 실행파일 전체를 한 번에 안 올림
```

대신:

```text
접근 시 page fault
→ 그때 디스크에서 읽음
```

즉:

```text
UNINIT 상태
→ fault 발생
→ FILE 또는 ANON으로 전환
```

---

# 11. Anonymous vs File-backed

## Anonymous Page

대표 예시:

* stack
* heap

특징:

* 원본 파일 없음
* eviction 시 swap disk 사용

---

## File-backed Page

대표 예시:

* ELF code
* mmap

특징:

* 원본 파일 존재
* clean 상태면 그냥 버려도 됨
* dirty 상태면 다시 write back 필요

---

# 12. Dirty Page란?

Dirty:

> 메모리 내용이 수정되었지만 아직 파일에 반영되지 않은 상태

예시:

```text
mmap된 메모리 수정
→ 아직 파일 저장 안 됨
```

Dirty면 eviction 시:

```text
파일에 다시 써야 함(write back)
```

Clean이면:

```text
그냥 버려도 됨
```

---

# 13. Page vs Frame

매우 중요

| 개념    | 의미                |
| ----- | ----------------- |
| Page  | 가상 메모리 단위         |
| Frame | 실제 물리 메모리(RAM) 단위 |

즉:

```text
Page = 가상
Frame = 물리
```

---

# 14. 페이지는 있는데 Frame은 없을 수 있다

Virtual Memory 핵심 개념

가능한 상태:

```text
SPT에는 존재
하지만 RAM에는 없음
```

이 상태에서 접근하면:

```text
page fault 발생
```

이후 흐름:

```text
1. SPT 조회
2. frame 할당
3. swap/file에서 읽기
4. page-frame 연결
5. PML4 매핑
```

---

# 15. Union 구조를 쓰는 이유

Pintos의 `struct page`는:

```c
union {
    struct uninit_page uninit;
    struct anon_page anon;
    struct file_page file;
}
```

구조를 사용합니다.

이유:

> "한 페이지는 동시에 여러 타입일 수 없기 때문"

즉:

```text
이 페이지는:
- anon 이거나
- file 이거나
- uninit 이다
```

동시에 둘 이상은 불가능.

그래서 union으로 메모리 절약 + 타입 분기 수행합니다. 

---

# 16. 전체 페이지 폴트 흐름

최종 흐름:

```text
유저가 가상주소 접근
↓
PML4에 매핑 없음
↓
Page Fault
↓
SPT 조회
↓
struct page 획득
↓
Frame 할당
↓
swap/file에서 데이터 로드
↓
PML4 매핑 생성
↓
실행 재개
```

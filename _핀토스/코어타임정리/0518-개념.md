## 260518 개념 코어타임 정리

이번 코어타임은 전체적으로 **Pintos VM 흐름**, 특히
`lazy loading → page fault → vm_do_claim_page → swap in/out → stack growth`
흐름을 중심으로 정리되었다. 

---

# 1. Lazy Loading 전체 흐름

## 1-1. load_segment()

실행 파일의 세그먼트를 페이지 단위로 나누어 처리한다.

흐름:

1. 실행 파일 세그먼트를 페이지 단위로 분리
2. 각 페이지마다

   * read_bytes
   * zero_bytes 계산
3. `vm_alloc_page_with_initializer()` 호출
4. 해당 페이지를 SPT에 등록
5. page를 `UNINIT` 상태로 생성
6. lazy load에 필요한 정보(aux)를 저장

핵심은:

```c
vm_alloc_page_with_initializer(
    VM_ANON,
    upage,
    writable,
    lazy_load_segment,
    aux
);
```

여기서 `lazy_load_segment` 함수 포인터와 aux 정보가 저장된다. 

---

# 2. Page Fault 발생 흐름

유저 프로그램이 아직 메모리에 없는 주소 접근 시:

```text
유저 접근
→ page fault
→ vm_try_handle_fault()
→ SPT에서 page 탐색
→ vm_do_claim_page()
```

이 흐름으로 들어간다. 

---

# 3. vm_do_claim_page()

가장 핵심 함수 중 하나.

역할:

1. 물리 프레임 확보
2. page ↔ frame 연결
3. PML4 mapping
4. swap_in 수행
5. CPU가 실제 접근 가능하도록 만듦

즉:

> "SPT에 있던 메타데이터를 실제 물리 메모리에 올리는 함수"

라고 정리 가능하다. 

---

# 4. struct page 와 page_operations

`struct page` 내부에는 page 타입별 동작 함수 테이블이 존재한다.

예시:

```c
struct page_operations {
    bool (*swap_in)(struct page *, void *);
    bool (*swap_out)(struct page *);
    void (*destroy)(struct page *);
};
```

즉 page 타입별로:

* swap_in
* swap_out
* destroy

동작이 달라진다. 

---

# 5. UNINIT Page의 핵심

초기 lazy loading 상태는 `UNINIT`.

UNINIT의 swap_in은:

```c
.swap_in = uninit_initialize
```

즉:

```text
swap_in(page)
→ uninit_initialize(page)
→ 실제 page 타입으로 변환
→ lazy_load_segment 실행
```

이 흐름이다. 

---

# 6. swap_in 매크로 흐름

실제로는 함수처럼 보이지만 매크로 치환이다.

개념적으로:

```c
page->operations->swap_in(page, kva)
```

UNINIT page면:

```c
uninit_ops.swap_in
→ uninit_initialize()
```

가 호출된다. 

---

# 7. Stack Growth 조건

stack growth는:

```c
addr >= rsp - 8
addr < USER_STACK
USER_STACK - upage <= 1MB
```

조건을 만족해야 한다.

의미:

| 조건                  | 의미               |
| ------------------- | ---------------- |
| `addr >= rsp - 8`   | 현재 stack 근처 접근인지 |
| `addr < USER_STACK` | stack 범위 안인지     |
| `<= 1MB`            | stack 최대 크기 제한   |

# 8. setup_stack()

초기 stack 생성 과정.

핵심:

```c
vm_alloc_page(VM_ANON | VM_MARKER_0, ...)
```

왜 `VM_MARKER_0`?

→ 이 anonymous page가 "stack" 용도임을 표시하기 위해. 

---

# 9. 왜 stack도 VM 관리 대상인가?

처음엔:

```text
main()
```

같은 초기 stack frame은 계속 사용할 것 같지만,

깊은 재귀 발생 시:

```text
main
→ foo
→ bar
→ ...
```

stack이 계속 아래로 성장한다.

그러면 오래전에 사용했던 main 근처 stack 영역은 최근 접근되지 않았기 때문에:

```text
swap out 대상
```

이 될 수 있다. 

즉:

> stack도 VM 시스템의 eviction 대상이다.

---

# 10. Victim Selection (Clock Algorithm)

메모리가 부족하면:

```text
vm_get_victim()
```

호출.

Clock Algorithm 사용.

동작:

1. accessed bit 확인
2. 1이면:

   * 0으로 변경
   * 다음 victim 탐색
3. 0이면:

   * eviction 대상 선택

CPU가 accessed bit를 자동으로 세팅한다. 

---

# 11. TLB Flush 이유

PTE 수정 후:

```text
TLB flush
```

필요.

이유:

CPU는 page table을 매번 직접 읽지 않고
TLB 캐시에 저장해두기 때문. 

---

# 12. swap_out 흐름

희생자 선택 후:

```text
swap_out(page)
→ backing store 저장
→ pml4_clear_page()
→ mapping 제거
```

진행. 

---

# 13. Lazy Load Segment 구현 아이디어

aux 구조체 예시:

```c
struct lazy_load_arg {
    struct file *file;
    off_t ofs;
    size_t read_bytes;
    size_t zero_bytes;
};
```

페이지별로:

* 어떤 파일
* 어디 offset
* 몇 byte 읽을지

SPT에 저장해둔다. 

---

# 14. file_reopen() 이유

하나의 inode를 여러 프로세스/페이지가 사용할 수 있기 때문.

`file_reopen()`은:

* 동일 inode 기반
* 새로운 file 객체 생성
* open count 증가

역할 수행. 

---

# 15. 현재 구현 우선순위 정리

현재 흐름상 추천 구현 순서:

```text
1. setup_stack
2. vm_alloc_page
3. supplemental page table
4. vm_do_claim_page
5. vm_get_frame
6. lazy_load_segment
7. stack growth
8. eviction
```

특히:

```text
setup_stack + lazy_load_segment
```

까지 구현하면 테스트가 본격적으로 돌기 시작한다고 정리됨. 

---

# 16. 스택 프레임 흐름 설명

함수 호출 시 실제 stack 구조:

```text
[ bar ]
[ return address to foo ]
[ foo ]
[ return address to main ]
[ main ]
```

함수 종료 시:

```text
stack pop
→ return address 복귀
```

형태로 동작. 

---

# 핵심 한줄 요약

이번 코어타임 핵심:

```text
SPT에 저장된 lazy page metadata를
page fault 발생 시
vm_do_claim_page()가 실제 물리 메모리로 연결해준다.
```

그리고:

```text
UNINIT page
→ swap_in
→ uninit_initialize
→ lazy_load_segment
```

흐름이 VM 전체의 핵심 연결 구조였다.
